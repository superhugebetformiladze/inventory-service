# План разработки inventory_service

**Создан:** 2026-09-02. **Все двенадцать этапов (0–11) пройдены к 2026-09-07.**

Два из них закрыты не полностью, и оба упираются в одно и то же — отсутствие
пилотных машин: этап 7 (установка службой и сбор проверены на одной версии
Windows, Windows 7 и 11 ждут пилота) и этап 11 (раскатка групповой политикой
написана и проверена на одной машине, самого пилота на десять машин нет).
Подробности — в записях этапов в `WORKLOG.md`.

Дальше — либо пилот на живых машинах, либо то, что отложено «после первой
версии» (см. ниже). Обе дороги упираются в два незакрытых вопроса владельцу:
про Active Directory (§14) и про подпись кода (§15).

Служба сбора сведений о рабочих станциях корпоративной сети и агент, который эти
сведения отдаёт. Самостоятельный продукт: у него несколько потребителей, и
учётная система — лишь первый из них.

## 1. Что строим

| Строим | Не строим |
|---|---|
| Приём отчётов от агентов, хранение снимков и их истории | Управление рабочими станциями, удалённое выполнение команд |
| Опознание машины и очередь неопознанных | Мониторинг доступности, сбор метрик нагрузки |
| Вычисление изменений и публикация событий в ленту | Учёт: инвентарные номера, ответственные, кабинеты — это учётная система |
| Очередь заданий «собрать сейчас» | Развёртывание ПО, установка обновлений |
| Агент под Windows: служба и автономный запуск с отчётом в файл | Агент под Linux/macOS — позже, если понадобится |
| Симулятор парка для разработки и нагрузочных прогонов | Сканер сети и SNMP — отдельным этапом после первой версии |

## 2. Инварианты

Нарушение любого из них — дефект, даже если код работает. Проверяются тестами,
а не договорённостью.

| # | Инвариант |
|---|---|
| I1 | **Сервис не знает своих потребителей.** Ни в коде, ни в контракте нет понятий учётной системы: `Entity`, «инвентарный номер», «рабочее пространство». Только `host`, `disk`, `nic`, `software` |
| I2 | **Запись в БД и публикация события — одна транзакция через outbox.** Публиковать в ленту прямо из обработчика запроса запрещено: упали между записью и публикацией — событие потеряно навсегда |
| I3 | **Каждый обработчик идемпотентен.** Сообщение придёт дважды — это не исключение, а норма доставки |
| I4 | **Ключ сообщения в ленте — идентификатор хоста.** Порядок гарантирован по машине; глобальный порядок не предполагается и на него нельзя опираться |
| I5 | **Контракт меняется только добавлением полей.** Удаление или переименование — новая версия топика и период, когда живут обе |
| I6 | **Агент не выполняет произвольных команд.** Виды заданий — закрытое перечисление в коде агента, а не строка из ответа сервера |
| I7 | **Отчёт принимается только с действующим ключом машины.** Ключ хранится хешем, отзывается по одной машине |
| I8 | **Неоднозначно опознанная машина не создаёт и не переписывает запись** — отчёт уходит в очередь разбора (уточнено 2026-09-03, см. §13) |
| I9 | **Событие публикуется только при фактическом расхождении** со свежим снимком. Совпавший отчёт обновляет отметку «на связи» и больше ничего |
| I10 | Секретов в коде и в git нет; всё из окружения, отсутствует переменная — сервис не стартует |
| I11 | Каждый внешний вызов с `context` и таймаутом. Бесконечных ожиданий не бывает |
| I12 | Миграции только вперёд, ревьюются, в entrypoint контейнера не запускаются |

## 3. Стек

Go (актуальная стабильная), PostgreSQL 16, Kafka — на разработке
[Redpanda](https://redpanda.com) как совместимая по протоколу замена: один
бинарник вместо JVM и ZooKeeper, все клиенты и инструменты те же.

| Задача | Выбор | Почему не иначе |
|---|---|---|
| HTTP | `net/http` + маршрутизатор стандартной библиотеки | Роутер с методами и путями есть в stdlib; chi добавил бы зависимость ради синтаксиса |
| БД | `pgx/v5` + `sqlc` | Запросы пишутся на SQL и проверяются компилятором; ORM здесь нечего давать |
| Миграции | `goose` | Простые, идут вперёд, живут файлами в репозитории |
| Kafka | `franz-go` | Чистый Go без cgo. `confluent-kafka-go` тянет C-библиотеку и ломает кросс-компиляцию агента под Windows |
| Логи | `log/slog`, JSON | В stdlib, структурные, со сквозным `trace_id` |
| Метрики | `prometheus/client_golang` | — |
| Тесты | `testing` + `testcontainers-go` | Настоящие Postgres и Redpanda в тестах, а не заглушки: половина дефектов здесь — на стыке |
| Служба Windows | `golang.org/x/sys/windows/svc` | — |
| Сбор данных | WMI | Единственный способ получить состав железа на Windows без сторонних агентов |
| Линт | `golangci-lint` | — |

Всё запускается через `make` и docker compose, включая тесты и линтеры.
Локальные `go test` не считаются прогоном.

```

├── cmd/
│   ├── server/          служба сбора
│   ├── agent/           агент рабочей станции (Windows)
│   └── simulator/       генератор отчётов: парк машин для разработки
├── internal/
│   ├── httpapi/         маршруты, аутентификация, троттлинг
│   ├── ingest/          приём и сохранение отчёта
│   ├── identity/        опознание машины по цепочке признаков
│   ├── diff/            сравнение снимков, вычисление изменений
│   ├── commands/        очередь заданий агентам
│   ├── outbox/          транзакционный outbox и релей
│   ├── publish/         запись в ленту
│   └── storage/         pgx, сгенерированный sqlc-код
├── pkg/contract/        ПУБЛИЧНЫЙ пакет: снимок и события
├── migrations/
```

`pkg/contract` вынесен наружу сознательно: его импортирует любой Go-потребитель.
Для потребителя не на Go в `docs/CONTRACT.md` лежит JSON-схема того же самого.

## 5. Хранилище

| Таблица | Что держит |
|---|---|
| `enrollment_tokens` | Токены регистрации: хеш, срок, остаток использований |
| `agents` | Агент: ключ хешем, версия, отметка «на связи», период опроса, отзыв |
| `hosts` | Машина: первое появление, последний отчёт, текущий снимок, состояние |
| `host_identifiers` | Признаки опознания: отметка агента, заводской номер, адрес карты |
| `snapshots` | Снимок целиком: `payload` в JSONB, время сбора и приёма, хеш |
| `changes` | Что именно изменилось: поле, было, стало |
| `commands` | Очередь заданий: вид, кто создал, когда выдано, результат |
| `unresolved_reports` | Отчёты неопознанных машин, ждущие человека |
| `outbox` | Сообщения к публикации: топик, ключ, содержимое, отметка публикации |

Снимки чистятся по сроку (30 дней), `changes` живут дольше — это история железа,
ради которой всё и затевается.

## 6. Топики ленты

| Топик | Ключ | Хранение | Содержимое |
|---|---|---|---|
| `inventory.snapshots.v1` | `host_id` | 30 дней | Полный снимок при каждом сборе |
| `inventory.hosts.v1` | `host_id` | уплотняемый | Актуальное состояние хоста. Новый потребитель читает его целиком и строит картину парка с нуля |
| `inventory.events.v1` | `host_id` | 90 дней | `host.first_seen`, `host.changed`, `host.silent`, `host.unresolved` |

Снимки и события разделены намеренно: снимок приходит всегда, событие — только
когда что-то произошло. Потребителю, которому нужны изменения, не надо разгребать
поток одинаковых снимков.

## 7. Этапы

Размер: **S** — до дня, **M** — несколько дней, **L** — неделя и больше.
Следующий этап не начинается, пока не выполнен Definition of Done текущего.

### Этап 0 — Каркас · S · ВЫПОЛНЕН 2026-09-02

Репозиторий, `go.mod`, `Makefile`, docker compose (postgres + redpanda + server),
`/health` и `/ready`, конфигурация из окружения, `slog` в JSON, `golangci-lint`, CI.

**DoD:** `make dev` поднимает стек, `/health` отвечает, `make ci` зелёный на пустом коде.

### Этап 1 — Контракт · M · ВЫПОЛНЕН 2026-09-02

`pkg/contract`: `Snapshot` и вложенные типы (`CPU`, `Memory`, `Disk`, `NIC`, `OS`,
`Software`), версия в самом сообщении, схемы событий. [`CONTRACT.md`](CONTRACT.md) с примерами JSON и правилом совместимости.

Делается до всего остального: контракт — это то, о чём договариваются две стороны
и три будущих потребителя, и менять его потом дороже, чем любой код.

**DoD:** пакет собирается, round-trip тесты сериализации проходят, по схеме из
документа сторонний потребитель может собрать свои структуры.

### Этап 2 — Сквозной путь · M · ВЫПОЛНЕН 2026-09-03

Тонкий скелет через всю систему: симулятор шлёт отчёт → сервер принимает
(аутентификация пока заглушка) → пишет снимок в БД → строка в outbox → релей
публикует в топик → тестовый потребитель печатает.

**Это самый важный ранний этап.** Риск проекта не в бизнес-логике, а на стыках:
outbox, публикация, потеря сообщения при падении. Скелет снимает этот риск
первым, а не последним.

**DoD:** `make demo` показывает путь отчёта от симулятора до топика; убийство
сервера между записью и публикацией не теряет сообщение.

### Этап 3 — Регистрация и ключи · M · ВЫПОЛНЕН 2026-09-03

Токен регистрации, `POST /v1/enroll`, выдача персонального ключа, хранение
хешем, отзыв по одной машине, middleware аутентификации, ограничение частоты.

**DoD:** отчёт без ключа, с чужим и с отозванным ключом отвергается; повторная
регистрация того же агента не создаёт вторую запись.

### Этап 4 — Опознание · M · ВЫПОЛНЕН 2026-09-03

Цепочка признаков: отметка агента → заводской номер → адрес сетевой карты →
очередь разбора. Таблица `host_identifiers`, `unresolved_reports`.

**DoD:** тесты на четыре сценария — переименование машины, замена диска, клон
виртуальной машины, новая машина. Ни в одном не создаётся дубликат хоста.

### Этап 5 — Дифф и события · M · ВЫПОЛНЕН 2026-09-03

Хеш снимка для быстрого «не изменилось», пофайловое сравнение для «что именно»,
запись в `changes`, публикация в три топика, события `first_seen` / `changed`,
beat-задача на `silent`.

**DoD:** одинаковый отчёт даёт ноль событий и ноль записей в `changes`;
изменение памяти даёт ровно одно событие; тысяча одинаковых отчётов подряд не
порождает ни одной публикации.

### Этап 6 — Задания · S · ВЫПОЛНЕН 2026-09-03

Очередь команд, `GET /v1/commands` коротким опросом, закрытый список видов
(`collect_now`, `set_interval`), приём результата, выдача ровно один раз.

**DoD:** задание выдаётся одному агенту один раз; падение агента после получения
не теряет задание навсегда; «собрать сейчас» отрабатывает за период опроса.

### Этап 7 — Агент · L

Служба Windows, сбор через WMI, файл отметки при первом запуске, расписание со
случайным сдвигом, буфер отчётов на диске при недоступности сервера, опрос
заданий, повторы с растущей задержкой, свой журнал.

Самый длинный этап: здесь и служба Windows, и WMI на разных версиях системы, и
поведение без сети.

Здесь же **автономный режим**: `agent --once --out отчёт.json` для машин без
сети, и приём таких файлов пачкой на стороне службы. Отчёт подписывается
ключом машины, иначе файл, принесённый на флешке, — это способ записать в
систему что угодно.

**DoD:** один exe; ставится как служба; переживает перезагрузку и сутки без
сети, после чего отчёты доходят; на трёх разных версиях Windows отдаёт
заполненный снимок; отчёт с машины без сети принимается файлом и даёт тот же
результат, что сетевой.

**Состояние на 2026-09-03:** написано всё. Сбор проверен на настоящей Windows
10 (машина разработчика) — прогон нашёл четыре ошибки, которых не показал ни
один тест. Остаются непроверенными установка службой, переживание
перезагрузки и сбор на Windows 7 и 11: нужны пилотные машины. Подробно —
запись этапа в `WORKLOG.md`.

### Этап 8 — Потребитель в учётной системе · M

Отдельное приложение внутри `AccountingSystemJSONB` (там своя граница и свои
инварианты): потребитель ленты, сопоставление полей снимка с атрибутами,
запись через `EntityService`, белый список атрибутов «заполняет машина»,
идемпотентность по паре хост-снимок, очередь расхождений.

**DoD:** изменение памяти на машине доезжает до карточки; поля, заполняемые
человеком, не затираются даже пустыми значениями; повторная доставка события
не создаёт вторую запись в журнале изменений.

**Выполнен 2026-09-04.** Потребитель живёт в `AccountingSystemJSONB`,
приложение `apps/inventory`; связь машины с карточкой — там же, отдельной
таблицей ([ADR-011](../../AccountingSystemJSONB/docs/adr/011-inventory-link-lives-in-consumer.md)).

### Этап 9 — Экраны · M

В карточке компьютера блок «Со слов машины» с возрастом сведений и кнопкой
«Обновить сейчас». Списки: агенты и их состояние, очередь разбора, расхождения,
история железа.

**DoD:** кнопка приводит к обновлению карточки в пределах периода опроса;
замолчавший агент виден в списке без поиска.

**Выполнен 2026-09-04.** Экраны — в учётной системе. В службе понадобился
административный вход `POST /v1/admin/hosts/{id}/collect`: кнопка «Обновить
сейчас» — единственный случай, когда потребитель обращается к службе сам, а не
читает ленту. Инвариант I1 цел: служба не знает, кто её просит, — знает, что
просящий предъявил ключ.

**Доделан 2026-09-07** по живому вопросу владельца: «нажимаю обновить, а
сведения не обновляются». Кнопка работала, агент отчитывался за две секунды —
но в ленту ничего не уходило, потому что состав машины не менялся, а состояние
публикуется только при расхождении. Отсюда `GET /v1/admin/hosts/{id}`: он
отвечает на единственный вопрос, на который лента ответить не может и не
должна, — «машина отвечает или молчит». Спрашивается по требованию человека,
открывшего карточку, а не расписанием: один запрос вместо пятисот сообщений в
час о том, что ничего не изменилось.

### Этап 10 — Эксплуатация · M

Метрики (принято отчётов, лаг потребителя, возраст последнего отчёта по парку),
алерт «замолчал», чистка снимков по сроку, резервная копия с проверкой
восстановлением, нагрузочный прогон симулятором.

**DoD:** утренний всплеск в тысячу отчётов за минуту не роняет сервис и не
теряет ни одного отчёта; лаг потребителя виден на графике.

**Выполнен 2026-09-07.** Прогон дал 1000 отчётов и 0 потерь; очередь публикации
разошлась в ноль. По дороге нашлись три дефекта, каждый из которых сломал бы
раскатку на живом парке, — подробности в `WORKLOG.md`. Доставка тревог не
настроена: адресат (почта, Telegram, дежурный) — решение владельца.

### Этап 11 — Развёртывание · M

Пакет установки, раскладка групповой политикой, обновление агента, инструкция
для ИТ-отдела.

**DoD:** установка на десять машин пилота без ручных действий на каждой.

**Выполнен 2026-09-07, кроме проверки на пилоте.** `make package` собирает
папку, которая кладётся в общую сетевую папку целиком; `rollout.cmd` —
сценарий запуска компьютера, он же обновление: сравнивает версию в пакете с
установленной и при совпадении выходит молча, не написав ни строки.
Инструкция — [РАЗВЁРТЫВАНИЕ.md](РАЗВЁРТЫВАНИЕ.md).

Отдельного механизма обновления нет намеренно: машина, пропустившая
обновление, догонит его при следующей загрузке, и вести список отставших не
нужно.

**Что проверить нельзя отсюда:** сам DoD. Десяти машин пилота нет, домена
нет, групповой политики нет. Проверено то, что проверяемо на одной машине:
совпадение версий даёт молчаливый выход с кодом 0, отсутствие `version.txt`
— код 1 и строку в журнале, адрес службы читается из `server.txt`. Ветка
обновления службы на живой машине ждёт подтверждения прав администратора.

Раскатка на пилоте упирается в незакрытый вопрос об Active Directory (§14) и
в решение о подписи кода (§15).

### Этап 12 — Коммутаторы по SNMP · M · ЛОГИКА ГОТОВА 2026-10-16

Опрос управляемых коммутаторов (D-Link DGS-1210/1100/3130) только на чтение:
порты, выученные MAC-адреса за ними, соседи по LLDP, ARP ядра. Результат —
уплотняемый топик `inventory.network.v1` (CONTRACT §5а).

* `internal/netscan` — сбор (`Collect`) за интерфейсом `Walker`: живой опрос
  (gosnmp, SNMPv2c) и файл `snmpwalk -On -Ox` — одна и та же логика;
* `network_devices` — последний снимок и отпечаток; в ленту — только при
  изменении (I9), снимок из файла старше записанного свежий не затирает;
* периодический опрос в службе — по `NETSCAN_TARGETS`; пусто — выключен;
* `agentctl netscan-import | netscan-poll | netscan-list`;
* `cmd/netscan` (`make netscan-exe`) — опрос с машины, у которой есть доступ к
  сети управления, в файлы для `netscan-import`.

**Дополнено 2026-10-20 — список от учёта, snmpwalk:**

* опрос — программой `snmpbulkwalk -v2c` из net-snmp (`NETSCAN_WALKER=snmpwalk`,
  по умолчанию; `gosnmp` — встроенная библиотека). Тем же, чем сеть проверяют
  руками; строка доступа — в `snmp.conf` (0600), не в аргументах процесса;
* список опроса — таблица `network_targets` (миграция 11): адреса из настроек
  (source `config`) и присланные внешней системой целиком
  (`PUT /v1/admin/network/targets`, свой `source`); перечитывается каждый
  проход, итог попытки — по адресу, и для ни разу не ответивших;
* `GET /v1/admin/network/targets` — список со статусом,
  `POST /v1/admin/network/poll` — внеочередной проход;
* опрос включается строкой доступа (`SNMP_COMMUNITY`), а не списком в настройках.

**Чего нет и почему:** сетевого доступа от службы к коммутаторам. Логика
проверена на обходах, составленных по MIB вручную (`internal/netscan/testdata`).
Первое, что сделать при появлении доступа, — `make netscan-poll TARGET=<ядро>
DRY=1` и сверить снимок с тем, что показывает веб-интерфейс коммутатора.

## 8. Порядок и почему он такой

Контракт первым, потому что его меняют дороже всего. Сквозной скелет вторым,
потому что главный риск проекта — на стыках, а не в логике. Агент седьмым, а не
первым, потому что до него всё проверяется симулятором: разработка не должна
зависеть от доступа к живым рабочим станциям. Потребитель восьмым, потому что
до этого нечего потреблять.

## 9. Риски

| Риск | Что делаем |
|---|---|
| WMI на старых версиях Windows отдаёт неполные или другие данные | Пилот на разнородных машинах не в конце, а сразу после этапа 7 |
| Антивирус блокирует неподписанный исполняемый файл | Выяснить про подпись кода до этапа 7, а не после жалоб |
| Kafka в эксплуатации: кто держит, как чинит, как бэкапит | Redpanda одним контейнером; порядок эксплуатации описать на этапе 10 |
| Разброс версий агента в парке после первых обновлений | Версия агента в каждом отчёте; список версий на экране агентов |
| Сопоставление полей окажется сложнее ожидаемого | Оно живёт в учётной системе и правится там; сервис от этого не зависит |

## 10. Условия, выясненные 2026-09-02

**Парк:** 500–1000 машин. В учётной системе заведено **543 карточки** типа
`computers` (28 атрибутов, все финальные — менять их нельзя).

**Часть машин вообще без сети.** Не «иногда вне периметра», а без доступа к
серверу в принципе. Push-агент до них не дотянется никогда, поэтому у сбора
два пути, а не один:

| Путь | Как работает |
|---|---|
| Сетевой | Агент-служба шлёт отчёты сама, получает задания опросом |
| Автономный | Тот же exe запускается разово, кладёт отчёт файлом рядом с собой; файл переносится и загружается в службу |

Формат отчёта в обоих путях один и тот же — это одна из причин, по которой
контракт делается первым этапом.

**Ключа опознания в учётной системе нет.** Ни одного атрибута с
`unique_in_type`, ни одного индексированного, атрибута с именем компьютера тоже
нет. Заголовок — `inventarnyy_nomer`, заполнен у всех 543 карточек, но агент
его не знает и знать не может.

> **Уточнено 2026-09-04, на живых данных.** Последнее утверждение оказалось
> неверным. Инвентарный номер В 495 КАРТОЧКАХ ИЗ 543 — это имя компьютера:
> заголовок выглядит как `PC038014`, и ровно так называется сама машина.
> Признак, объявленный здесь недоступным, всё это время лежал на виду.
>
> Ожидание меняется с «свяжется около пятой части парка» на «свяжется почти
> весь». Подбор в потребителе идёт по двум признакам: сперва MAC — физический,
> потом имя — административный.
>
> Там же нашлось, что часть заголовков набрана в русской раскладке: `РС064001`
> с кириллическими Р и С. Сравнение строк этого не прощает, поэтому имена
> приводятся к латинице перед сравнением.
>
> Урок общий: таблица заполненности атрибутов отвечает на вопрос «что
> заполнено», но не на вопрос «что там написано». Второй вопрос надо задавать
> отдельно, и задавать его надо данным, а не схеме.

Отсюда решение: **связь «хост ↔ карточка» живёт в потребителе**, отдельной
таблицей внутри приложения синхронизации, а не атрибутом типа. Атрибуты
учётной системы не трогаются вовсе (I1 соблюдён с обеих сторон).

Автоматически связать удастся немногое — заполненность атрибутов на 543
карточках:

| Атрибут | Заполнен | Годится для связывания |
|---|---|---|
| `inventarnyy_nomer` | 543 из 543 | Агент его не знает |
| `operatsionnaya_sistema` | 508 | Не признак машины |
| `polzovatel` | 403 | Подсказка оператору, не ключ |
| `obem_operativnoy_pamyati_gb` | 379 | Не признак машины |
| `protsessor`, `zhestkiy_disk_ssd_m2` | 369 | Не признак машины |
| `ip` | 308 | Меняется при DHCP, ненадёжен |
| `mac_adres` | **105** | Единственный настоящий признак |

То есть автоматически свяжется около пятой части парка, остальное — человеком
через очередь разбора, с подсказками по пользователю, кабинету и IP. Это
несколько часов работы оператора, растянутых на время внедрения, и об этом
надо сказать заранее, а не обнаружить на этапе 9.

Удешевить можно необязательным параметром установки: если тот, кто ставит
агента, знает инвентарный номер машины — он передаёт его при установке, и
связывание происходит сразу. Для машин без сети обход кабинетов всё равно
неизбежен, поэтому там это почти бесплатно.

**Развёртывание сервера:** внутри локальной сети, наружу не смотрит.

## 12. Решение по хранению дисков в учётной системе

Принято 2026-09-02, применяется на этапе 8.

Что есть сейчас: атрибут `zhestkiy_disk_ssd_m2`, строка, заполнен у 369
карточек из 543. Значения — свободный текст про объём: `1Тб`, `128 GB`,
`1TB, 240GB`, `250Гб`, `1.2Тб`, `240 Gb (ssd)`. Модель не пишет никто; у 74
карточек перечислено несколько дисков через запятую.

То есть поле фактически отвечает на один вопрос — «сколько места», — но
отвечает строкой, по которой нельзя ни отфильтровать, ни построить отчёт.

**Решение — два атрибута вместо одного:**

| Атрибут | Тип | Зачем |
|---|---|---|
| `obem_diskov_gb` | decimal, индексируемый, в списке | Суммарный объём. То, ради чего поле существует: «у кого меньше 256 ГБ», сортировка, отчёты |
| `nakopiteli` | string, в карточке | Человекочитаемая сводка от агента: `SSD 240 ГБ Samsung 870 EVO · HDD 1 ТБ WD Blue` |

`zhestkiy_disk_ssd_m2` после переноса удаляется. Перенос — разовый разбор
существующих значений в `obem_diskov_gb`; состав до первого отчёта агента
неизвестен и остаётся пустым.

**Почему сводка строкой, а не атрибутом типа `json`.** Проверено в коде
фронтенда: `json`-атрибут выводится в карточке как `JSON.stringify(value)`,
то есть сырым текстом, и правится в текстовом поле. Список дисков в таком виде
человек читать не будет.

**Почему полный состав не кладётся в карточку вообще.** Модель, серийный
номер, наработка и S.M.A.R.T. каждого диска живут в `inventory_service` — это
его данные, и он про них знает всё. На экран учётной системы их можно вывести
отдельным блоком на этапе 9, не заводя ни одного атрибута. Инвариант I1 при
этом цел с обеих сторон: служба не знает слова «атрибут», учётная система не
хранит того, чем не управляет.

**Когда это решение придётся пересмотреть:** если понадобится запрос «все ПК с
диском модели X» — тогда диски становятся дочерними объектами со своим типом.
Это ×3–4 объекта в базе и заметно сложнее слияние, поэтому не сейчас.

## 13. Уточнение инварианта I8 — 2026-09-03

Исходная формулировка звучала так: «неопознанная машина не создаёт запись
сама — уходит в очередь разбора». При реализации четвёртого этапа выяснилось,
что она смешивает две разные вещи.

**Что она защищала на самом деле:** появление дубликата уже известной машины.

**Что получалось буквально:** каждая новая машина парка попадала бы в очередь
разбора — все 500–1000 при первой раскатке. Разбирать там нечего: машина
новая, признаки её ничему не противоречат, а реестр службы — её собственный, и
машина обязана в него как-то попасть.

**Уточнение.** Реестр машин службы наполняется сам, когда признаки
непротиворечивы и среди них есть надёжный (заводской номер или SMBIOS UUID).
В очередь разбора уходят три случая, где автоматика ошибётся молча:

| Случай | Как выглядит | Почему нельзя решать самому |
|---|---|---|
| Признаки указывают на разные машины | Сетевую карту переставили из одной машины в другую | Выбор наугад портит обе карточки |
| Под известной отметкой пришёл другой заводской признак | Клон виртуальной машины или замена материнской платы | Снаружи это одно и то же, а машин в первом случае две, во втором одна |
| Нет ни одного надёжного признака | Сборная машина без заводского номера | Запись, заведённая по адресу карты, при её замене превратится в дубликат |

Связь машины с **карточкой учёта** — отдельный вопрос, и он остаётся ручным:
там очередь разбора работает так, как описано в §10, и живёт на стороне
потребителя (этап 8).

## 15. Подпись кода и раскатка агента — решение отложено, варианты

Вопрос всплыл на седьмом этапе: агент — это исполняемый файл, который ставится
службой на пятьсот машин. Неподписанный exe в корпоративной сети встречает
SmartScreen, политики ограниченного запуска и антивирус, и каждая из этих
встреч заканчивается машиной, на которой агента нет, — молча.

| Вариант | Чего стоит | Что даёт |
|---|---|---|
| Не подписывать | Ничего | Работает, пока политики мягкие. На жёстких — тихие пропуски при раскатке |
| Самоподписанный сертификат + раздача корневого через групповую политику | Час работы, если AD есть | Полноценное доверие внутри домена, ноль денег. Вне домена бесполезно |
| Коммерческий сертификат подписи кода | 10–20 тыс. ₽ в год, проверка организации | Доверие везде, включая машины вне домена |

**Рекомендация:** самоподписанный, если есть Active Directory и внутренний
центр сертификации; коммерческий — только если машин вне домена много. Ответ
упирается в незакрытый вопрос об AD из §14.

Раскатка при наличии AD — сценарий запуска компьютера в групповой политике:

```
\server\share\agent.exe install -server http://inventory:8080 -token enr_…
```

Токен раскатки один на всю кампанию, ограничен сроком и числом машин; агент
стирает его из своих настроек сразу после регистрации. Машины вне домена —
руками или тем же файлом с флешки, автономным режимом.
