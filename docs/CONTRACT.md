# Контракт

То, о чём договариваются агент, служба и все потребители ленты. Исходник —
пакет [`pkg/contract`](../pkg/contract); этот документ нужен потребителям не
на Go.

**Версия контракта: 1.**

---

## 1. Правило совместимости

Контракт меняется **только добавлением полей**. Удаление поля, переименование,
смена типа или смысла — это новая версия топика и период, когда живут обе.

Причина не в аккуратности, а в том, что стороны обновляются не одновременно:
агент на пятистах машинах доедет до новой версии за недели, а служба
обновится сегодня. Всё это время старые агенты шлют старый снимок, а новые
потребители читают ленту, где лежат сообщения обеих версий.

Отсюда два обязательства, одинаковых для всех:

* **Читатель игнорирует незнакомые поля**, а не падает на них. Разбор с
  «запретить неизвестные поля» в этом проекте запрещён и проверяется тестом.
* **Писатель не рассчитывает**, что читатель понял новое поле.

## 2. Единицы измерения

Единица — в имени поля: `size_bytes`, `total_bytes`, `speed_mbits`,
`diagonal_inch`, `power_on_hours`. Время — всегда UTC, формат RFC 3339.

Это не занудство. В учётной системе, откуда переносятся данные, объём дисков
записан строками «1Тб», «128 GB», «1.2Тб», «240 Gb (ssd)» — ровно потому, что
единицу когда-то оставили на усмотрение заполняющего. Договориться один раз
дешевле, чем потом разбирать 369 значений регулярным выражением.

### Поля, у которых есть неочевидный смысл

| Поле | Смысл |
|---|---|
| `agent_id` | Отметка агента: записана при первом запуске и больше не меняется. Первое и самое надёжное звено опознания — переименование машины и замена диска её не трогают |
| `agent_version` | После первого же обновления в парке живут две-три версии агента. На вопрос «почему у этих машин нет поля X» отвечает только это поле |
| `collected_at` | Когда **сняли**, а не когда доставили. По нему отбрасываются устаревшие снимки: доставка не гарантирует порядок |
| `origin` | `network` — агент отправил сам; `offline` — снято на машине без сети и принесено файлом |
| `machine.serial` | Заводской номер из BIOS. На сборных машинах бывает заглушкой («To Be Filled By O.E.M.», «Default string») — такие значения служба считает отсутствующими |
| `machine.uuid` | Идентификатор SMBIOS. Стабильнее серийного номера, но у клонированных виртуальных машин совпадает, поэтому не первое звено опознания |
| `interfaces[].virtual` | VPN, Hyper-V, loopback. В опознании не участвуют: их адреса меняются от запуска к запуску |
| `disks[].health` | Пустое значение означает «не знаем», а **не** «здоров» |
| `disks[].power_on_hours` | Наработка в часах. Заполняется, только когда агент работает от администратора или SYSTEM — служба агента работает именно так — и диск отдаёт счётчик надёжности. Пусто — «не знаем», и тогда причина лежит в `failures` с разделом `disk_hours`: отказ в доступе или «Windows не вернула ни одного счётчика». В сравнение снимков не входит: растёт с каждым отчётом |
| `failures` | Что собрать не удалось. Без этого поля снимок без дисков неотличим от машины без дисков, и служба честно запишет «диски исчезли» |

### Что проверяется при приёме

Только то, без чего дальше нельзя:

* версия контракта указана и не новее поддерживаемой;
* отметка агента непустая;
* способ доставки известен;
* время сбора не в будущем больше чем на 30 минут (часы на станциях врут) и
  не старше полугода (отчёт с флешки может пролежать недели — это нормально,
  но год это уже археология);
* есть хотя бы один признак для опознания.

**Полнота сбора не проверяется.** Частичный снимок — норма: WMI на старой
Windows регулярно отдаёт не всё. Отказ от такого снимка означал бы, что машина
с нечитаемым S.M.A.R.T. вообще не попадёт в учёт.

## 4. События

Топик `inventory.events.v1`, ключ сообщения — `host_id`.

```json
{
  "schema_version": 1,
  "type": "host.changed",
  "host_id": "01J8ZC3K7Q1X",
  "occurred_at": "2026-09-02T08:30:04Z",
  "snapshot_id": "01J8ZC3K7Q20",
  "changes": [
    { "field": "memory.total_bytes", "old": "8 ГБ", "new": "16 ГБ" }
  ]
}
```

| Вид | Когда | `host_id` |
|---|---|---|
| `host.first_seen` | Машина опознана впервые и заведена в службе | обязателен |
| `host.changed` | Состав или сеть изменились. Публикуется **только при фактическом расхождении** | обязателен |
| `host.silent` | Машина не выходила на связь дольше порога. Порождается задачей службы, а не отчётом | обязателен |
| `host.unresolved` | Пришёл отчёт от машины, которую опознать не удалось. Запись при этом **не создаётся** | пуст |

Значения в `changes` — строки, потому что потребитель показывает их человеку
(«было 8 ГБ, стало 16 ГБ»), а не считает по ним. Для счёта есть сам снимок.

`host.changed` без единого изменения контрактом запрещён: это и есть тот шум,
ради борьбы с которым заведено правило «событие только при расхождении».

## 5. Состояние хоста

Топик `inventory.hosts.v1`, **уплотняемый**: хранится последняя запись по
каждому ключу, навсегда.

```json
{
  "schema_version": 1,
  "host_id": "01J8ZC3K7Q1X",
  "first_seen_at": "2026-04-01T10:00:00Z",
  "last_report_at": "2026-09-02T08:30:00Z",
  "snapshot": { "...": "последний снимок целиком" },
  "silent_since": null,
  "retired": false
}
```

Запись обновляется **при изменении состава, при уходе в молчание и при
возвращении на связь** — не на каждый отчёт. Отсюда следствие, о котором
обязан знать каждый потребитель: `last_report_at` в этом топике означает
«когда состояние машины последний раз менялось», а НЕ «когда машина последний
раз выходила на связь». Считать по нему молчание нельзя — так молчащим
объявляется весь парк, в котором просто ничего не менялось. Для молчания есть
`silent_since`, и ставит его служба.

`silent_since` — с какого момента служба считает машину молчащей; `null`
означает «на связи». Поле есть и в состоянии, и в событии `host.silent`
одновременно намеренно: событие рассказывает тому, кто слушает ленту сейчас, а
состояние отвечает тому, кто прочитает уплотняемый топик через месяц.

Смысл отдельного топика: новый потребитель читает его целиком и строит картину
всего парка с нуля — не разбирая тридцатидневную историю снимков и не
спрашивая службу ни о чём.

`retired` вместо удаления записи: в уплотняемом топике запись нельзя просто
стереть, иначе потребитель, читающий с начала, никогда не узнал бы о выбытии
машины. Поэтому выбытие — тоже сообщение.

Проверено дорогой ценой: тысяча машин нагрузочного прогона была удалена из
базы службы напрямую, и при первом же чтении ленты все они приехали в очередь
разбора учётной системы — в топике они остались, а надгробия им никто не
отправил. Выводит машину `agentctl retire`.

Сообщение о выбытии несёт последний снимок машины, если он есть. Пустые поля в
нём означают «не знаем», а не «стало пусто»: затирать ими то, что потребитель
уже знает, нельзя — иначе списанная машина превращается в безымянную строку с
одним идентификатором.

**Выбытие отменяется отчётом.** Машина, выведенная из учёта, но продолжающая
отчитываться, возвращается в парк, и об этом уходит новое состояние — уже без
`retired`. Значит вывели по ошибке либо не сняли агента; в обоих случаях
оставить отметку означало бы, что служба считает машину выбывшей, а все
потребители получают от неё свежие сведения и считают живой. Отчёт — это
доказательство, и оно сильнее прежнего решения человека.

## 5а. Сетевые устройства

Топик `inventory.network.v1`, **уплотняемый**, ключ — `device_id`. Состояние
управляемого коммутатора, собранное по SNMP (только чтение). Публикуется при
первом опросе и при фактическом изменении (I9); неизменившееся устройство в
ленту не уходит, сколько бы раз его ни опрашивали.

```json
{
  "schema_version": 1,
  "device_id": "88:76:b9:c8:89:80",
  "first_seen_at": "2026-10-16T09:00:00Z",
  "last_polled_at": "2026-10-16T09:30:00Z",
  "device": {
    "schema_version": 1,
    "device_id": "88:76:b9:c8:89:80",
    "management_ip": "192.168.4.172",
    "chassis_mac": "88:76:b9:c8:89:80",
    "sys_name": "sw-412",
    "sys_descr": "DGS-1210-26 Gigabit Ethernet Switch",
    "sys_object_id": "1.3.6.1.4.1.171.10.76.28.2",
    "collected_at": "2026-10-16T09:30:00Z",
    "ports": [
      {
        "if_index": 2, "number": 2, "name": "1/2", "alias": "бухгалтерия",
        "admin_up": true, "oper_up": true, "speed_mbps": 100, "pvid": 20,
        "macs": ["00:15:65:aa:bb:cc", "70:85:c2:44:55:66"]
      },
      {
        "if_index": 25, "number": 25, "name": "1/25",
        "admin_up": true, "oper_up": true, "speed_mbps": 1000, "pvid": 1,
        "macs": ["00:11:22:33:44:55"],
        "neighbor": {"chassis_id": "00:11:22:33:44:55", "port_id": "1/0/5", "sys_name": "core"}
      }
    ],
    "arp": [{"ip": "192.168.9.65", "mac": "00:15:65:aa:bb:cc"}]
  }
}
```

| Поле | Смысл |
|---|---|
| `device_id` | MAC шасси (`dot1dBaseBridgeAddress`, иначе LLDP). Нет ни того, ни другого — `ip:<адрес>` |
| `ports` | Порты моста и физические интерфейсы (ifType 6/62/69/117). Интерфейсы VLAN и служебные не входят |
| `number` | Номер порта моста (BRIDGE-MIB), он же номер на лицевой панели. 0 — вне моста |
| `macs` | Адреса, выученные за портом (FDB, статусы learned и mgmt). Собственные (self) не входят |
| `neighbor` | Сосед по LLDP: `chassis_id` — MAC, если сосед так объявился; `port_id` — как сосед назвал свой порт |
| `arp` | ARP-таблица. Непуста у устройства, которое маршрутизирует (ядро) |
| `silent_since` | С какого момента устройство не отвечает на опрос. Есть — устройство молчит дольше порога (`NETSCAN_SILENCE`, по умолчанию четыре периода опроса); `device` в таком сообщении — последний известный снимок. Снимается следующим сообщением без этого поля, когда устройство ответило |

Выводов в сообщении нет (I1): «магистральный порт», «на порту принтер» —
решение потребителя. Служба сообщает, что видит коммутатор.

Таблица MAC-адресов меняется при каждом включении компьютера, поэтому
сообщения по коммутатору доступа приходят несколько раз в день — это
изменения, а не шум.

## 6. Приведение значений

**Адреса сетевых карт** приводятся к виду `a4:bb:6d:11:22:33` — строчные, через
двоеточие. WMI отдаёт `A4-BB-CC-DD-EE-FF`, `ip` отдаёт `a4:bb:...`; без
приведения опознание сочло бы это двумя машинами.

Приводит агент, но служба **нормализует повторно**: доверять чужой
нормализации в вопросе, от которого зависит склейка карточек, нельзя.

**Внешние диски** (`interface: "USB"`) не входят в суммарный объём: флешка,
забытая в машине на момент сбора, не должна выглядеть как выросшее хранилище и
порождать событие об изменении.

## 7. Отчёт с машины без сети

Часть парка не имеет сети вовсе. Такие машины снимают сведения в файл, файл
переносят к службе, и она принимает его тем же приёмом, что и сетевой отчёт:
те же проверки, то же опознание, та же лента. Разница одна — файл подписан.

Подпись обязательна, потому что без неё файл на флешке есть способ записать в
учёт что угодно от имени любой машины.

### Конверт отчёта

```json
{
  "schema_version": 1,
  "agent_id": "4fbdd94c-657d-4811-989d-5e99686efd5d",
  "algorithm": "ed25519",
  "signature": "<подпись поля snapshot, base64>",
  "snapshot": { "...": "обычный снимок, origin = offline" }
}
```

Подпись считается по БАЙТАМ поля `snapshot` — по тем самым, что лежат в файле,
а не по разобранной и заново собранной структуре. Пересборка меняет порядок
полей и формат чисел, и честная подпись переставала бы сходиться. Отсюда
следствие для любого, кто будет писать такие файлы сам: конверт нельзя
переформатировать после подписи.

Проверяющая сторона обязана:

1. взять открытый ключ по `agent_id` из конверта;
2. проверить подпись **до** разбора содержимого;
3. убедиться, что `agent_id` внутри снимка совпадает с тем, что снаружи;
4. убедиться, что `origin` равен `offline`.

Пункт 3 закрывает подмену отметки: снаружи она подписью не покрыта, а по ней
ищется ключ. Пункт 4 закрывает переигрывание перехваченного сетевого отчёта.

### Заявка на регистрацию

Машина без сети не может обменять токен раскатки на ключ по сети, и заявка
идёт тем же путём — файлом:

```json
{
  "schema_version": 1,
  "agent_id": "4fbdd94c-657d-4811-989d-5e99686efd5d",
  "hostname": "PC-214-01",
  "agent_version": "0.7.0",
  "enrollment_token": "enr_…",
  "key_hash": "<sha256 ключа доступа, hex>",
  "key_prefix": "inv_AbCdEfGh",
  "public_key": "<открытый ключ машины, base64>",
  "created_at": "2026-09-03T10:00:00Z",
  "signature": "<подпись заявки без поля signature, base64>"
}
```

Право зарегистрироваться даёт токен раскатки — тот же, что и по сети. Подпись
здесь про другое: без неё открытый ключ подменяется по дороге, и дальше
поддельные отчёты принимаются уже без всякого токена.

Ключ доступа машина придумывает себе сама и отдаёт службе только его хеш —
ровно так же, как при регистрации по сети, где сам ключ службе тоже не
остаётся. Поэтому машина, однажды оказавшись в сети, пользуется уже имеющимся
ключом.
