# Деплой службы на сервер

Рабочий сервер службы инвентаризации: первый запуск, команды эксплуатации,
копии, обновление, откат.

Служба разворачивается **на одном сервере с учётной системой**. Общий порядок
для обеих, адрес сервера и перенос данных — в документации учётной системы,
`AccountingSystemJSONB/docs/DEPLOYMENT.md`. Раскатка агентов на рабочие
станции — [РАЗВЁРТЫВАНИЕ.md](РАЗВЁРТЫВАНИЕ.md).

---

## 1. Что поднимается

`deploy/docker-compose.prod.yml` — отдельный файл, а не оверлей поверх
разработческого. Оверлей наследует всё, что в нём не перекрыто, а списки в
Compose при слиянии складываются: в учётной системе именно так рабочая база
осталась с портом, открытым в сеть.

| Контейнер | Что | Наружу |
|---|---|---|
| `server` | служба | **8090** — единственный порт |
| `db` | PostgreSQL 16 | нет |
| `redpanda` | лента | нет |
| `topics` | разовый шаг: топики с правильными политиками | — |
| `migrate`, `agentctl` | разовые команды, профиль `tools` | — |
| `prometheus`, `grafana` | графики, профиль `metrics`, необязательно | 3001 |

### Отличия от разработки

**Служба — собранный бинарник**, а не `go run` по смонтированным исходникам. В
образе три программы: `server`, `migrate` и `agentctl`. Без двух последних
рабочий сервер оказался бы сервером, на котором нельзя ни обновить схему, ни
выпустить токен раскатки — компилятора в рабочем образе нет.

**Лента в рабочем режиме, и это включено явно.** Образ Redpanda оставляет
`developer_mode` и кэширование записи включёнными даже без флага разработчика —
проверено на этой версии образа. Кэширование подтверждает сообщение раньше, чем
оно легло на диск: выключение питания потеряло бы сообщения, которые служба уже
отметила опубликованными, и повторно их не отправил бы никто. Настройки
применяются при каждом старте: `redpanda.yaml` живёт в слое образа, а не в томе.

**Топики заводит шаг `topics`, автосоздание выключено.** Автоматически
заведённый топик получает политику по умолчанию — удаление записей через
неделю. Для `inventory.hosts.v1` это поломка контракта: он обещает последнюю
запись по каждой машине навсегда, и на этом держится подъём нового потребителя
с нуля. В разработке топик уплотняемый потому, что его однажды завели руками.
Шаг стоит в зависимостях службы и выполняется при каждом `up`, поэтому забыть
его нельзя. Он же выставляет настройки заново каждый раз: `create || true`
оставил бы уже существующий неправильный топик как есть.

| Топик | Политика |
|---|---|
| `inventory.hosts.v1` | уплотняемый — последняя запись по машине навсегда |
| `inventory.snapshots.v1` | 30 дней |
| `inventory.events.v1` | 90 дней |

**Обмен с учётной системой — через общую сеть Docker** `inventory-feed`, а не
через порт ленты. Лента без аутентификации, открытая в локальную сеть, — это
способ для любого компьютера сети записать в карточки учёта что угодно. Сеть
создаёт служба, поэтому она поднимается первой.

**Журналы контейнеров ограничены**: 5 файлов по 20 МБ.

**Имя образа — `inventory-service`**, а не `inventory-server`, как у
разработческого. Одинаковое имя значило бы, что сборка рабочего образа на машине
разработчика подменяет разработческий, и следующий `make up` запускает `go run`
в образе без компилятора.

## 2. Первый запуск

```bash
cd /srv/inventory_service
cp .env.prod.example .env.prod
nano .env.prod
```

| Переменная | Что |
|---|---|
| `POSTGRES_PASSWORD` | `openssl rand -base64 32` |
| `ADMIN_TOKEN` | `openssl rand -base64 32`; тот же ключ — в `INVENTORY_ADMIN_TOKEN` учётной системы |
| `APP_VERSION` | метка версии, например `2026-09-14` |

Без `POSTGRES_PASSWORD` или `ADMIN_TOKEN` Compose откажется поднимать стек и
назовёт недостающую переменную.

```bash
make prod-build
make prod-migrate
make prod-up
```

Ожидаемо:

```
$ make prod-migrate
схема на версии 8

$ make prod-up
 Container inventory-topics-1  Exited
 Container inventory-server-1  Healthy

$ curl -s http://localhost:8090/ready
{"checks":{"kafka":"ok","postgres":"ok"},"status":"ready"}
```

`topics` в состоянии `Exited` — так и должно быть: шаг разовый.

## 3. Эксплуатация

| Команда | Что |
|---|---|
| `make prod-ps` | состояние контейнеров |
| `make prod-logs` | журнал службы |
| `make prod-agents` | зарегистрированные машины, версия агента, последний отчёт |
| `make prod-token LABEL="раскатка" DAYS=14 USES=600` | токен раскатки |
| `make prod-ctl ARGS="pending"` | очередь разбора |
| `make prod-ctl ARGS="retire -name PC-01"` | вывести машину из учёта |
| `make prod-ctl ARGS="dismiss -report <id> -reason «чужой ноутбук»"` | закрыть отчёт, не заводя машину |
| `make prod-ctl ARGS="revoke -agent <отметка> -reason «…»"` | отозвать ключ машины |
| `make prod-backup` | копия базы с проверкой восстановлением |
| `make prod-metrics` | Prometheus и Grafana (нужен `GRAFANA_ADMIN_PASSWORD`) |

Состояние службы словами — «что не так и что делать» — показывает и сама
учётная система, на вкладке «Инвентаризация».

## 4. Копии

```bash
make prod-backup
```

Снимает копию, восстанавливает её во временную базу и сверяет: число машин,
снимков, изменений, агентов и то, что JSON снимков читается. Копия, которую ни
разу не восстанавливали, — это не копия, а файл.

В `/etc/crontab` или `sudo crontab -e`:

```cron
30 3 * * *  cd /srv/inventory_service && make prod-backup >> /var/log/backup-inventory.log 2>&1
```

Копии складываются в `backups/`. Их нужно забирать на другую машину: сервер, на
котором лежат и данные, и копии, — одна точка отказа.

**Ленту копировать не нужно.** Всё, что в ней лежит, восстанавливается из базы
службы: состояние машин публикуется заново при первом же изменении, а
потребитель учётной системы хранит своё у себя.

## 5. Обновление и откат

```bash
cd /srv/inventory_service
git pull
make prod-backup
make prod-build   APP_VERSION=2026-10-01
make prod-migrate APP_VERSION=2026-10-01
make prod-up      APP_VERSION=2026-10-01
```

Затем записать версию в `APP_VERSION` в `.env.prod`. Переменная из командной
строки сильнее значения в файле — поэтому обновиться можно, не правя файл, а
записать версию после того, как всё поднялось.

**Откат** — прежний образ остался на сервере:

```bash
make prod-up APP_VERSION=2026-09-14
```

Если новая версия успела применить миграцию, откат кода без отката схемы
возможен только при совместимой назад миграции. Иначе — восстановление из копии,
снятой перед обновлением.

## 6. Переезд с машины разработчика

**Базу разработки на сервер не переносить.** В ней следы наладки: тысяча машин
нагрузочного прогона, выведенных из учёта, тестовые сценарии опознания,
закрытая очередь разбора. Рабочая служба начинается с чистой базы, и машины
заводятся сами при первом отчёте.

**Машины, где агент стоял во время разработки, регистрируются заново.** Их
ключи знает только база разработки, и новая служба их не признает: агент
запишет «ключ машины не признан службой: нужна повторная регистрация» и
отчитываться перестанет. На такой машине:

1. `удалить-полностью.cmd` — снимает службу и стирает отметку со старым ключом;
2. `установить.cmd` из пакета, где `server.txt` указывает на новый сервер, а в
   `token.txt` — свежий токен.

## 7. Проверено

2026-09-14, на машине разработчика, рядом с разработческим окружением — под
другим именем проекта и портом:

* сборка образа: в `/usr/local/bin` — `agentctl`, `migrate`, `server`;
* миграции отдельным шагом — схема на версии 8;
* шаг `topics` — три топика, `inventory.hosts.v1` с `cleanup.policy=compact`;
* лента: `developer_mode: 0`, `write_caching_default: false`,
  `auto_create_topics_enabled: false`;
* наружу опубликован только порт службы; у базы и ленты — ни одного;
* `agentctl token` из рабочего образа выпускает токен;
* административный маршрут отвечает по ключу и отдаёт 401 без него;
* настоящий агент этой машины, зарегистрированный во временном каталоге,
  отчитался; служба приняла отчёт, лента донесла его до потребителя учётной
  системы через общую сеть;
* `make prod-backup`: копия снята, восстановлена, содержимое сверено.

**Не проверено:** сервер на Linux и его сеть — проверка шла на Docker Desktop;
раскатка на пилотные машины.
