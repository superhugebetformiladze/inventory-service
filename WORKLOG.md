### Решения этапа

**`/health` не проверяет зависимостей, `/ready` проверяет.** Если подмешать
базу в проверку живости, перезапуск базы начнёт убивать саму службу:
оркестратор сочтёт её мёртвой и перезапустит, хотя чинить надо не её.

**Проверка готовности на этапе 0 — обычный TCP-набор до соседей.** Настоящих
клиентов ещё нет, но знать, поднялся ли Postgres, уже надо. Проверки заменятся
на честные, когда появятся клиенты (этап 2). Зависимостей это не потребовало —
весь этап на стандартной библиотеке.

**Ошибка настроек называет все недостающие переменные сразу.** Падать по одной
за запуск — это пять перезапусков вместо одного.

### Что пришлось поправить по ходу

* **Порт 5433 занят** учётной системой `AccountingSystemJSONB`, которая работает
  на той же машине. Postgres службы вынесен на 5434, остальные порты тоже
  смещены от стандартных. Причина записана в `.env.example`.
* **`go test -race` не запускался** в контейнере: детектору гонок нужен cgo. В
  `Dockerfile.dev` добавлены `gcc` и `musl-dev`, включён `CGO_ENABLED=1`.
  Отказываться от `-race` нельзя: служба будет писать из нескольких горутин, и
  гонки ловятся только так.
* **Линтер нашёл три места** с `httptest.NewRequest` без контекста — заменено на
  `NewRequestWithContext`. Мелочь, но правило I11 («всё внешнее с контекстом»)
  либо действует везде, либо не действует.
* **Правка тестов через Windows сломала форматирование:** файл записался с CRLF,
  и `gofmt` в контейнере счёл его неотформатированным. Добавлен `.gitattributes`
  с `eol=lf`, файл переформатирован.
* **`make.ps1` не запускался:** PowerShell 5.1 читает UTF-8 без BOM как ANSI,
  кириллица в сообщениях разваливалась и ломала кавычки, а за ними и разбор
  всего скрипта. Файл пересохранён с BOM. При правке `make.ps1` BOM надо
  сохранять — иначе поломка вернётся.

## 2026-09-02 · Этап 1 — контракт · ВЫПОЛНЕН

Пакет `pkg/contract`: снимок машины, события и состояние хоста. Публичный, а
не `internal`, потому что его импортируют три стороны сразу — агент, служба и
любой Go-потребитель. Держи он структуры внутри, каждый потребитель переписал
бы их у себя, и однажды одна из копий разошлась бы с остальными молча.

### Создано

| Файл | Что в нём |
|---|---|
| `pkg/contract/doc.go` | Правило совместимости и правило единиц измерения — то, ради чего пакет вообще отдельный |
| `pkg/contract/snapshot.go` | `Snapshot` и вложенные типы, `NormalizeMAC`, отбор физических интерфейсов и суммарный объём дисков |
| `pkg/contract/event.go` | Четыре вида событий, `Change`, `HostState` для уплотняемого топика |
| `pkg/contract/validate.go` | Проверка снимка и события, `UsableSerial` |
| `pkg/contract/snapshot_test.go`, `validate_test.go` | 20 тестов |
| `docs/CONTRACT.md` | То же самое для потребителя не на Go: примеры JSON и смысл неочевидных полей |

### Решения этапа

**Единица измерения — в имени поля** (`size_bytes`, а не `size`). Прямое
следствие того, что нашлось в учётной системе: 369 значений объёма дисков
записаны как «1Тб», «128 GB», «1.2Тб», «240 Gb (ssd)» — единицу когда-то
оставили на усмотрение заполняющего. Договориться один раз дешевле, чем потом
разбирать это регулярным выражением.

**Поле `failures` — что собрать не удалось.** Без него снимок без дисков
неотличим от машины без дисков: служба записала бы «диски исчезли», а
потребитель — «диск вынули». Частичный сбор это норма, а не сбой, и проверка
снимка полноту намеренно **не** требует.

**`origin`: сетевой отчёт или принесённый файлом.** Разные пути доставки для
одного и того же контракта — иначе машины без сети не охватываются вовсе.
Отсюда же разный допуск на возраст снимка: отчёт с флешки месячной давности
принимается, годовой — нет.

**`UsableSerial` отсекает заглушки производителя** — «To Be Filled By O.E.M.»,
«Default string», «None». Формально это непустая строка; опознание по ней
склеило бы в одну машину весь сборный парк.

**Виртуальные интерфейсы не участвуют в опознании.** Адрес VPN-адаптера
меняется от подключения к подключению — по нему машина становилась бы новой
при каждом входе в сеть из дома.

**Внешние диски не входят в суммарный объём.** Флешка, забытая в машине на
момент сбора, иначе выглядела бы как выросшее хранилище и порождала событие об
изменении.

**`retired` вместо удаления записи** в уплотняемом топике: стереть её нельзя,
иначе потребитель, читающий с начала, никогда не узнает о выбытии машины.

### Definition of Done — выполнен

```
gofmt / go vet / golangci-lint    чисто, 0 issues
go test ./... -race -count=1      ok, 4 пакета
```

Отдельным тестом закреплено главное обязательство контракта: **разбор не
падает на незнакомых полях**. Инвариант I5 держится именно на этом — агент на
пятистах машинах обновляется неделями, и всё это время в ленте лежат сообщения
обеих версий.

Зависимостей по-прежнему ноль: весь контракт на стандартной библиотеке.

## 2026-09-03 · Этап 2 — сквозной путь · ВЫПОЛНЕН

Отчёт проходит систему насквозь: симулятор → HTTP → проверка контрактом →
запись в базу → outbox → релей → лента. Функциональности здесь почти нет —
этап нужен, чтобы снять главный риск проекта, а он не в бизнес-логике, а на
стыках.

### Создано

| Файл | Что в нём |
|---|---|
| `migrations/00001_initial.sql` | `hosts`, `snapshots`, `outbox`; частичный индекс по неотправленным |
| `migrations/embed.go` | Встраивание миграций в бинарник |
| `internal/storage/storage.go` | Пул pgx, накат миграций, версия схемы |
| `internal/storage/snapshots.go` | `SaveSnapshot` — снимок и сообщения ленты одной транзакцией |
| `internal/storage/outbox.go` | `ProcessPending` — выборка, отправка и отметка в одной транзакции |
| `internal/publish/kafka.go` | Отправитель поверх franz-go, имена топиков |
| `internal/outbox/relay.go` | Релей с растущей отсрочкой при недоступной ленте |
| `internal/ingest/ingest.go` | Приём: проверка, нормализация, сборка сообщения |
| `internal/httpapi/reports.go` | `POST /v1/reports` |
| `cmd/migrate/`, `cmd/simulator/` | Накат миграций и парк машин для разработки |
| Тесты релея и приёма | 13 тестов |

Зависимости добавлены впервые: `pgx/v5`, `goose/v3`, `franz-go`, `google/uuid`.
Каждая закрывает то, что стандартной библиотекой не делается.

### Решения этапа

**Отправка идёт внутри транзакции базы.** Первая версия `FetchPending`
выбирала строки `FOR UPDATE SKIP LOCKED` запросом по пулу — то есть
блокировка снималась сразу после выборки, и второй релей взял бы те же
строки. Переделано в один транзакционный проход `ProcessPending`: выбрать,
отправить, отметить. Пачки маленькие именно поэтому.

**Отметка `published_at` — после отправки, а не до.** Осознанный перекос:
упасть между отправкой и отметкой можно, тогда сообщение уйдёт повторно.
Обратный порядок дал бы потерю, а потеря необратима, тогда как дубль
обрабатывается идемпотентным потребителем (I3).

**Ключ идемпотентности приёма — время сбора**, а не хеш содержимого. Повтор
после обрыва связи несёт то же самое время; новый сбор через четыре часа
несёт другое, даже если машина не изменилась ни на байт. Хеш склеил бы два
разных факта в один.

**Отметка «на связи» двигается и на повторе.** Агент выходил на связь — это
факт, независимый от того, изменилось ли что-нибудь. I9 запрещает публиковать
событие, а не обновлять отметку.

**Служба нормализует адреса сетевых карт повторно за агентом.** Доверять чужой
нормализации в вопросе, от которого зависит склейка карточек, нельзя: агент
старой версии или самописный отправитель пришлют «AA-BB-CC», и заведётся
вторая машина.

**Проверки готовности переведены на настоящих клиентов.** На этапе 0 это был
TCP-набор до соседей; открытый порт не означает, что база принимает запросы.

**Опознание пока сведено к отметке агента** и помечено в коде как временное:
цепочка признаков и очередь разбора — этап 4.

### Что пришлось поправить по ходу

* **`go:embed` не смотрит выше своего каталога** — встраивание вынесено в
  `migrations/embed.go`, пакет живёт в самом каталоге миграций.
* **Линтер нашёл четыре вещи**, все по делу: слабый генератор в симуляторе
  (оставлен осознанно, воспроизводимость парка важнее непредсказуемости, с
  пометкой и объяснением), преобразование `int`→`byte` (убрано переходом на
  `rng.Read`), комментарий, похожий на испорченную директиву встраивания, и
  мёртвая функция разбора кода ошибки — приём построен на `ON CONFLICT`, и
  она не понадобилась.
* **Ошибка проверки задваивалась**: агент получал «отчёт негоден: снимок
  негоден: …». Приставка убрана из контракта — её добавляет вызывающий.
* **`docker compose up -d --build` не перезапускает службу** после правки
  кода: код монтируется томом, образ не меняется, контейнер не пересоздаётся.
  Добавлена цель `restart`; на этом потерялось десять минут отладки «почему
  правка не подействовала».

### Definition of Done — выполнен на живом стеке

Главная проверка — падение между записью в базу и публикацией:

```

2. симулятор: 4 отчёта                   служба приняла все, HTTP 201

## 2026-09-03 · Этап 3 — регистрация и ключи · ВЫПОЛНЕН

Маршрут приёма закрыт. Агент обменивает токен раскатки на персональный ключ,
и без действующего ключа отчёт не принимается. Ключ отзывается по одной
машине.

### Создано

| Файл | Что в нём |
|---|---|
| `migrations/00002_agents.sql` | `enrollment_tokens`, `agents`, ссылка `hosts.agent_uuid` |
| `internal/agents/keys.go` | Генерация токенов и ключей, хеширование, показываемый префикс |
| `internal/agents/service.go` | Регистрация и проверка ключа |
| `internal/storage/agents.go` | Запросы: обмен токена, поиск по хешу, отзыв, список |
| `internal/httpapi/auth.go` | `POST /v1/enroll` и проверка ключа перед приёмом |
| `internal/httpapi/throttle.go` | Ограничитель частоты по адресу |
| `cmd/agentctl/` | Токены, список агентов, отзыв ключа |
| Тесты | 24 новых: ключи, регистрация, отказы, ограничитель |

### Решения этапа

**Два разных секрета с разными правами.** Токен раскатки не даёт права слать
отчёты — только право обменяться на персональный ключ. Разница существенная:
токен один на всю раскатку и рано или поздно утечёт, потому что лежит в
скрипте групповой политики, который видит весь домен. Поэтому у него срок и
счётчик использований, а отзывается по одной машине уже выданный ключ.

**SHA-256 вместо bcrypt — осознанно, а не по недосмотру.** Медленные хеши
нужны там, где секрет выбирает человек: они делают перебор словаря дорогим.
Здесь секрет — 256 случайных бит, перебирать его нечем. Зато медленный хеш
стоил бы десятков миллисекунд на КАЖДОМ отчёте от пятисот машин и лишил бы
возможности искать агента по ключу одним запросом по индексу.

**Отметка агента берётся из ключа, а не из тела отчёта.** Иначе машина с
действующим ключом присылает отчёт от имени соседа и переписывает его
карточку. Несовпадение при этом не сглаживается молча: это либо ошибка в
агенте, либо попытка подмены, и оба случая надо видеть — 400 и запись в
журнал.

**Одна ошибка на все причины отказа.** «Токен просрочен» против «такого
токена нет» — это подсказка тому, кто подбирает. Наружу уходит «не принят»,
подробности остаются в журнале службы.

**Повторная регистрация той же отметки перевыпускает ключ, а не отказывает.**
Так выглядит установщик, который получил ключ, но не успел сохранить, и
переустановленная машина. Идентификатор машины при этом сохраняется — иначе
терялась бы её история. Событие пишется в журнал предупреждением: так же
выглядела бы и попытка увести чужую отметку.

**Обмен токена — одной транзакцией с блокировкой строки токена.** Иначе два
установщика, стартовавшие одновременно с токеном на одно применение, оба
увидели бы «остался один» и оба зарегистрировались.

**Без проверки ключей маршрутов агента нет вовсе.** Если `Auth` не собран,
`Router` не регистрирует ни `/v1/enroll`, ни `/v1/reports`. Открытый приём —
это возможность записать в учёт что угодно от имени любой машины, и такой
режим не должен получаться случайно, из-за недособранной зависимости. На это
есть тест.

**Ограничитель частоты написан свой, сорок строк.** Токен раскатки можно
подбирать со скоростью сети; с ограничением подбор 192-битного секрета
бессмыслен окончательно. Заголовки вроде `X-Forwarded-For` намеренно не
читаются: их подделывает кто угодно, и ограничитель, доверяющий им,
обходится одной строкой в запросе. Когда перед службой появится обратный
прокси, доверенный источник адреса придётся задать явно.

**В журнал попадает только начало ключа.** Журналы читают, копируют и
пересылают; ключ из журнала — это работающий ключ.

### Definition of Done — выполнен на живом стеке

```
отчёт без ключа                → 401 + WWW-Authenticate
отчёт с чужим ключом           → 401
регистрация с чужим токеном    → 401 «токен регистрации не принят» (без причины)
регистрация с верным токеном   → 201, ключ выдан один раз
отчёт с выданным ключом        → 201
отзыв ключа                    → следующий отчёт той же машины 401
токен на 2 использования       → 201, 201, 401
чужая отметка в теле отчёта    → 400, до приёма не доходит

Симулятор переведён на тот же путь, что у настоящего агента: сначала
регистрация, потом отчёты с ключом. Проверять приём в обход регистрации
значило бы проверять не то, что работает в жизни.

## 2026-09-03 · Этап 4 — опознание · ВЫПОЛНЕН

Отметка агента перестала быть единственным способом узнать машину. Появилась
цепочка признаков, очередь разбора и правило «в спорном случае решает человек».

### Создано

| Файл | Что в нём |
|---|---|
| `internal/identity/identity.go` | Сбор признаков из снимка и **чистая** функция решения |
| `internal/identity/identity_test.go` | 12 тестов, из них четыре — те самые сценарии, на которых такие системы ломаются |
| `migrations/00003_identity.sql` | `host_identifiers`, `unresolved_reports`, перенос старых отметок |
| `internal/storage/identity.go` | Поиск признаков, закрепление, очередь разбора, ручная связка |
| `cmd/agentctl` | Команды `pending` и `link` |

### Главное решение: логика опознания — чистая функция

`identity.Decide` не знает ни про базу, ни про транзакции: на входе признаки из
снимка и то, что о них знает база, на выходе — что делать. Поэтому четыре
сценария, на которых всё ломается, проверяются тестами без базы вообще, за
сорок миллисекунд, и читаются как описание поведения:

```
TestСценарийПереименованиеМашины
TestСценарийЗаменаДискаОтметкаПотеряна
TestСценарийКлонВиртуальнойМашины
TestСценарийНоваяМашина
```

### Решения этапа

**Первичный ключ `(kind, value)` в `host_identifiers`.** Один признак
принадлежит не более чем одной машине — это правило базы, которое нарушить
нельзя, а не соглашение в коде, которое однажды нарушат.

**Признаки делятся на надёжные и слабые.** Адрес сетевой карты — слабый: карту
переставляют из машины в машину, и запись, заведённая по одному лишь адресу,
завтра окажется чужой. Поэтому по адресу машину можно **найти**, но нельзя
**завести**.

**Одной отметки агента для заведения машины тоже мало.** Её выдаёт себе сам
агент, и переустановленная система принесёт новую. Машина, заведённая только
по ней, при первой же переустановке превратится в дубликат.

**Машина запоминает новые признаки при каждом опознании.** Найденная по
заводскому номеру после переустановки, она тут же получает новую отметку
агента — и следующий отчёт находится сразу по ней, коротким путём.

**Клон виртуальной машины и замена материнской платы — один и тот же случай
снаружи.** Под известной отметкой приходит другой заводской номер. В первом
случае машин две, во втором одна, и различить их автоматике нечем. Оба идут к
человеку — и это правильный ответ, а не отговорка.

**Отложенный отчёт при разборе НЕ применяется к данным машины.** Человек
связывает его с машиной, признаки закрепляются, но сам снимок уже устарел:
следующий придёт через несколько часов и придёт уже опознанным. Применять
старый снимок задним числом значило бы откатывать карточку к состоянию на
момент, когда её никто не смотрел.

**Неопознанный отчёт — успех для агента (202), а не ошибка.** Его дело
доставить отчёт, а не разбираться, чей он. Ответ ошибкой заставил бы агента
повторять вечно то, что чинится только человеком.

**Событие `host.unresolved` публикуется с ключом «отметка агента».** Машины
ещё нет, ключа-машины тоже; порядок внутри одной неопознанной машины при этом
сохраняется. Само событие нужно потребителю не ради данных, а чтобы он показал
очередь разбора: иначе отчёты копятся там, куда никто не смотрит.

### Уточнение инварианта I8

Исходная формулировка — «неопознанная машина не создаёт запись сама» — при
реализации оказалась смешивающей две разные вещи. Буквально она означала бы,
что **каждая** новая машина парка идёт в очередь разбора: все 500–1000 при
первой раскатке, и разбирать там нечего.

Уточнено до «**неоднозначно** опознанная машина не создаёт и не переписывает
запись». Реестр машин службы наполняется сам, когда признаки непротиворечивы
и среди них есть надёжный. В разбор идут три случая, где автоматика ошиблась
бы молча. Подробно — `docs/PLAN.md` §13.

Связь машины с **карточкой учёта** это уточнение не трогает: она остаётся
ручной и живёт на стороне потребителя (этап 8).

### Definition of Done — выполнен на живом стеке

Четыре сценария:

```
новая машина с заводским номером     → заведена, first_seen
та же машина переименована           → тот же host_id
диск заменён, отметка новая          → тот же host_id, новая отметка запомнена
клон виртуальной машины              → 202, очередь разбора
```

Ещё два случая, где автоматика ошиблась бы:

```
сборная машина без заводского номера  → 202 «нет ни одного надёжного признака»
сетевая карта переставлена            → 202 «признаки указывают на разные машины»
```

Дубликатов не возникло ни в одном: у машины с номером `SER-AAA1` одна запись и
две отметки агента.

Полный круг разбора:

```
agentctl pending                     → три отчёта с причинами
agentctl link -report .. -host ..    → признаки закреплены за машиной
следующий отчёт той же машины        → 201, опознан сам, тот же host_id
```

## 2026-09-03 · Этап 5 — дифф и события · ВЫПОЛНЕН

Служба перестала быть приёмником и стала источником: она замечает, что
изменилось, и сообщает об этом. Появилась история железа — то, ради чего всё
затевалось.

### Создано

| Файл | Что в нём |
|---|---|
| `internal/diff/diff.go` | Чистое сравнение снимков и отпечаток |
| `internal/diff/diff_test.go` | 20 тестов, половина — про тишину там, где ничего не произошло |
| `migrations/00004_changes.sql` | `changes`, `hosts.fingerprint`, `hosts.silent_since` |
| `internal/storage/changes.go` | Быстрый путь по отпечатку, запись расхождений, пометка молчащих |
| `internal/silence/` | Наблюдатель за машинами, переставшими выходить на связь |
| Правки `ingest` | События `host.changed`, состояние в уплотняемый топик |

### Главное решение: сравнивается не всё подряд

В снимке полно того, что меняется само по себе: время последней загрузки,
наработка диска в часах, адрес VPN-адаптера, забытая в машине флешка.
Сравнивай снимки целиком — и девятнадцать отчётов из двадцати давали бы
«изменилось», а настоящая замена диска утонула бы в этом потоке.

Поэтому в `diff.go` лежит явный список полей, и он же отвечает на вопрос «о
чём стоит будить человека». Половина тестов пакета проверяет именно **тишину**:
одинаковые снимки, выросшая наработка, воткнутая флешка, подключённый VPN,
дособранные агентом сведения, пропущенный сбор программ.

### Решения этапа

**Отпечаток считается по тем же полям, что сравнение.** Иначе быстрый путь не
срабатывал бы никогда (если в отпечаток попадает время сбора) или срабатывал
бы ложно (если в нём нет чего-то, что смотрит сравнение). Второе и случилось —
см. ниже.

**Появление значения на пустом месте — не изменение.** Агент обновился и
научился читать материнскую плату: это событие про агента, а не про железо.
Иначе выкатка новой версии агента дала бы «изменилось» по всему парку.

**Пустой список программ — это «не собрали», а не «программ нет».** У агента
не хватило прав на реестр; считать это удалением всех программ значило бы
породить событие о сотне удалений на ровном месте.

**Длинный список программ сворачивается в счёт.** После обновления системы
список меняется на десятки позиций; перечислять их все — сделать историю
машины нечитаемой.

**Состояние машины в уплотняемый топик пишется только при изменении.** Топик
хранит последнюю запись по каждому ключу навсегда, и новый потребитель читает
его целиком. Писать в него на каждый отчёт — гонять пятьсот одинаковых
сообщений в час ради состояния, которое не менялось.

**`silent_since` — отдельная колонка, а не вычисление на лету.** Без неё
событие о молчании уходило бы на каждом проходе задачи, пока машина стоит
выключенная в отпуске владельца. Сбрасывается при первом же отчёте — иначе
машина, замолчавшая однажды, больше никогда бы об этом не сообщила.

**Первый отчёт после обновления службы не даёт «изменилось всё».** У известной
машины отпечатка ещё нет; вместо сравнения с пустотой он молча запоминается, и
сравнение начинается со следующего отчёта.

### Дефект, найденный живой проверкой

Состояние диска по S.M.A.R.T. **не входило в отпечаток**. Быстрый путь отвечал
«ничего не менялось», и сличение снимков до состояния диска не доходило вовсе:
переход `OK → Pred Fail` пропадал молча. Человек узнал бы о сыплющемся диске
только когда тот умер.

Причина — ровно та, о которой предупреждает комментарий в самом файле:
состояние намеренно не входит в `diskKeys` (иначе «диск заменили» срабатывало
бы на ухудшении здоровья того же диска), а отпечаток строился из `diskKeys`.

Исправлено отдельным полем `Health` в проекции. Тест
`TestОтпечатокЗамечаетУхудшениеДиска` закрепляет правило: **отпечаток обязан
покрывать всё, что смотрит `Compare`** — иначе быстрый путь глушит расхождение
молча.

Дефект не нашли ни тесты пакета (они сравнивали снимки напрямую, минуя
отпечаток), ни тесты приёма. Нашла проверка на живом стеке — как и два
предыдущих раза.

### Definition of Done — выполнен на живом стеке

Главная проверка, инвариант I9:

```
первый отчёт                        → 201, событие host.first_seen
+ 60 отчётов, отличаются только
  временем сбора и наработкой диска → 61 снимок в базе
                                       0 записей об изменениях
                                       1 событие (то самое первое)

```

```

адрес 10.0.9.5 → .77     → interfaces.ipv4
диск Pred Fail → Bad     → disks.health: SSD 240 ГБ Samsung 870: Pred Fail -> Bad

## 2026-09-03 · Этап 6 — задания · ВЫПОЛНЕН

Появилась кнопка «Обновить сейчас» — точнее, то, что стоит за ней. Человек
ставит задание, агент забирает его при ближайшем опросе.

### Создано

| Файл | Что в нём |
|---|---|
| `pkg/contract/command.go` | Закрытый список видов заданий, `Command`, `CommandResult`, проверка |
| `migrations/00005_commands.sql` | `commands`, заполнение `hosts.agent_uuid` |
| `internal/storage/commands.go` | Постановка, выдача с арендой, приём результата, поиск агента по машине |
| `internal/commands/commands.go` | Прикладной слой очереди |
| `internal/httpapi/commands.go` | `GET /v1/commands`, `POST /v1/commands/{id}/result` |
| `cmd/agentctl` | Команды `collect` и `commands` |
| Тесты | 11 новых |

### Главное решение: список видов заданий лежит в контракте

Не в службе, а в `pkg/contract` — и это не вопрос раскладки файлов. Агент
сверяет полученное с этим перечислением и **отказывается от всего
остального**. Не «сервер прислал строку — выполним», а «сервер может попросить
одно из двух».

Разница в том, что произойдёт, если службу однажды взломают. С закрытым
списком на стороне агента взломанная служба может попросить пятьсот машин
собрать сведения и поменять период сбора. Без него — что угодно.

Проверка стоит на обеих сторонах одним и тем же кодом: служба проверяет,
прежде чем поставить в очередь, агент — прежде чем выполнить. Вторая проверка
не лишняя: агент не должен доверять тому, что служба прислала правильное.

### Решения этапа

**Выдача не окончательна: у задания есть аренда.** Агент мог упасть, потерять
сеть или быть выключенным сразу после получения. Без возврата одно падение
агента означало бы навсегда потерянное «собрать сейчас», и человек ждал бы
ответа, которого не будет. Через пять минут невыполненное задание снова
доступно, счётчик попыток растёт — по нему видно, что агент берёт задание и
не справляется.

**Выдача — одним запросом, а не «выбрать, потом обновить».** Два опроса от
одного агента, пришедшие одновременно (агент перезапустился, старый процесс
ещё жив), иначе получили бы одно и то же задание дважды.

**У задания есть срок годности.** «Собрать сейчас», поставленное в
понедельник ноутбуку, уехавшему в отпуск, иначе сработает через три недели —
когда никому уже не нужно и никто не помнит, зачем просили.

**Задание адресовано агенту, а не машине.** Спрашивает сервер именно агент, по
своему ключу. Ссылка на машину рядом — чтобы человек мог сказать «собери с
ПК-214», не зная про отметки агентов. Связь `hosts.agent_uuid` заведена ещё на
третьем этапе, но заполнять её было нечем до опознания; теперь проставляется
при каждом принятом отчёте.

**Проверка принадлежности задания — в самом запросе к базе.** Без неё агент с
действующим ключом мог бы закрыть чужое задание и оставить соседа ждать вечно.

**Период сбора ограничен снизу и сверху.** Пятьсот машин, собирающих сведения
каждую секунду, положат и себя, и службу; «раз в год» не должно выглядеть
работающей настройкой.

**Опрос заданий — самый частый запрос ко всей службе.** Пятьсот агентов раз в
минуту, и почти всегда ответ пустой. Поэтому обработчик не делает ничего,
кроме одного запроса по частичному индексу, а индекс не трогает выполненные
задания.

### Definition of Done — выполнен на живом стеке

```
1. агент опрашивает            → {"commands":[]}
2. человек: collect -host PC-CMD → задание поставлено
3. агент опрашивает            → выдано одно задание collect_now
4. агент опрашивает снова      → пусто: дважды не выдаётся
5. агент отчитался             → 204

чужой агент закрывает задание  → 404
аренда истекла, агент молчит   → задание вернулось в очередь, попыток 2
неизвестный вид задания        → в очередь не попадает
```

Проверки кода: `gofmt`, `go vet`, `golangci-lint` — 0 issues; `go test -race`
— 10 пакетов, 115 тестов.

## 2026-09-03 · Этап 7 — агент · ВЫПОЛНЕН ЧАСТИЧНО

| Тесты | 34 новых |

### Главное решение: автономный отчёт подписывается парой ключей, а не общим секретом

Отчёт, принесённый на флешке, надо чем-то подтверждать: иначе файл — это
способ записать в учёт что угодно от имени любой машины, достаточно поправить
в нём имя и объём диска.

Очевидный ход — подписать ключом машины — не работает. Служба хранит только
ХЕШ ключа (см. `agents.Hash`) и проверить подпись им не может. Пришлось бы
либо держать ключи машин в открытом виде, и тогда одна утечка базы даёт право
писать в учёт от имени всего парка, либо не проверять подпись вовсе.

Поэтому пара ключей: закрытый остаётся на машине, открытый уезжает службе при
регистрации. Открытый ключ не секрет, подделать им ничего нельзя, и утечка
базы по-прежнему ничего не даёт. Ed25519 из стандартной библиотеки — новых
зависимостей это не потребовало.

Машина без сети зарегистрироваться не может, и заявка идёт тем же путём —
файлом. Право даёт тот же токен раскатки, что и по сети; ключ доступа машина
придумывает себе сама и отдаёт службе только его хеш, ровно как по сети.
Подпись на заявке нужна не для права, а для целостности: без неё открытый ключ
подменяется по дороге, и дальше поддельные отчёты принимаются уже без всякого
токена.

### Решение: сбор разрезан на «спросить систему» и «собрать снимок»

Запросы к WMI, реестру и `/proc` живут в файлах с ограничением по платформе.
Всё, что превращает ответы в снимок контракта, — обычные функции, которые
ничего у системы не спрашивают.

Разрез не косметический. Файл с WMI нельзя прогнать нигде, кроме живой
Windows, и логика внутри него не проверялась бы вовсе. А проверять там есть
что: разбор даты WMI (сдвиг хранится в МИНУТАХ, и деление на 60 в Индии и
Иране даёт получасовую ошибку), коды типа памяти (на Windows 10 и Windows 7
одно и то же число означает разное), вид накопителя (достоверный ответ даёт
только `MSFT_PhysicalDisk`, которого нет на Windows 7), разбор EDID монитора.
Всё это — обычные тесты, идущие в контейнере с Linux.

### Решения этапа

**Мониторы — из EDID в реестре, а не из WMI.** `WmiMonitorID` отдаёт названия
массивами шестнадцатибитных чисел, и работа с ними через COM зависит от версии
библиотеки. EDID — 128 байт с зафиксированной раскладкой, одинаковой на всех
версиях Windows; его разбор проверяется тестом с настоящим блоком монитора.

**Программы — из реестра, и это принципиально.** Класс `Win32_Product`,
которым их обычно достают, при каждом обращении запускает проверку целостности
КАЖДОГО установленного пакета MSI: на рабочей станции это минуты нагрузки и
записи в журнал установки. Реестр отвечает мгновенно и содержит то же самое.

**Буфер отчётов ограничен двумястами.** Машина, простоявшая полгода без сети,
иначе завалит службу разом. Выбрасываются самые старые: свежие сведения нужнее
прошлогодних.

**Отвергнутый отчёт не откладывается.** Служба, признавшая отчёт негодным,
признает его негодным и завтра. Агент, который этого не различает, забивает им
очередь навсегда и перестаёт отправлять всё остальное. Поэтому ошибки клиента
разделены на три вида: временная (повторить), отказ (выбросить), ключ не
признан (звать человека).

**Накопленное уходит перед свежим.** Служба сравнивает снимки по времени
сбора; отправить свежий раньше отложенных значит потерять историю простоя.

**Расписание с разбросом, первый сбор — не сразу.** Пятьсот машин включаются
утром в одни и те же десять минут. Сбор «сразу при старте» превратил бы это в
залп по свежезагруженной службе. Служба Windows ставится с отложенным
автозапуском, а внутри агента расписание разбросано на десятую часть периода.

**Токен раскатки стирается из настроек сразу после регистрации.** Он действует
на все машины сразу, а установщик кладёт его в файл на каждой из пятисот.
Оставить его лежать — значит завести пятьсот копий ключа от всего парка.

**Каталог данных не удаляется при снятии службы.** В нём отметка агента.
Снятая и поставленная заново служба должна остаться той же машиной в учёте, а
не завести вторую карточку.

### Что нашёл живой прогон

Три дефекта, которых не было видно в тестах.

**1. Очередь разбора росла по строке на каждый отчёт.** Машина, которую не
удаётся опознать, шлёт отчёты дальше — каждые четыре часа. Одна такая машина
даёт шесть строк в сутки; на парке, где заводского номера нет у трети машин,
очередь за неделю перестаёт быть списком дел и становится журналом. Теперь
повторный отчёт обновляет уже лежащую запись, а счётчик показывает, сколько
раз машина приходила (`00007_unresolved_dedup.sql`).

**2. Событие `host.unresolved` уходило в ленту на каждый повторный отчёт.**
Нарушение I9 в чистом виде и то же самое по последствиям: потребитель получает
одно и то же событие шесть раз в сутки на каждую неразобранную машину. Теперь
оно уходит один раз — при первом появлении.

**3. Очередь разбора наполовину не работала.** Отчёт машины без заводского
номера и без SMBIOS UUID — а это весь сборный парк — попадал в разбор при
первом же появлении, и связать его было НЕ С ЧЕМ: машины в базе ещё нет.
Человек видел запись, которую нельзя ни принять, ни отклонить. Добавлена
команда `agentctl link -report <id> -new`: человек говорит «да, это новая
машина», она заводится, признаки закрепляются, следующий отчёт опознаётся сам.
Заодно `link` принимает укороченный идентификатор — тот, что печатает
`pending`: полный UUID в таблице из шести колонок нечитаем.

Плюс два огреха поменьше. Шаг главного цикла (10 с) был грубее периода опроса
и тихо превращал настройку «спрашивать раз в пять секунд» в «раз в десять».
И подпись автономного отчёта ломалась о собственное форматирование файла:
`json.MarshalIndent` переформатировал уже подписанные байты.

### Зависимости

Три новые, все только для Windows; в бинарник службы они не попадают.

| Зависимость | Зачем |
|---|---|
| `golang.org/x/sys` | Служба Windows и реестр. Разговаривать с диспетчером служб по его протоколу больше нечем |
| `github.com/yusufpapurcu/wmi` | Запросы к WMI |
| `github.com/go-ole/go-ole` | COM, на котором стоит WMI |

Рассматривался вариант без них — вызывать `powershell -Command Get-CimInstance`.
Отклонён: служба, которая пятьсот раз в сутки на пятистах машинах запускает
powershell.exe, выглядит для любого антивируса ровно как то, с чем он борется.

### Definition of Done — проверено на живом стеке

```
1.  регистрация по сети            → ключ выдан, токен стёрт из настроек
2.  отчёт по сети                  → принят
3.  службы нет                     → отчёт отложен, назначен повтор
4.  сеть вернулась                 → накопленное доставлено, очередь пуста
5.  задание «собрать сейчас»       → получено, выполнено, закрыто
6.  машина без сети                → заявка и подписанный отчёт файлом
7.  приём файлов службой           → заявка принята, отчёт принят
8.  подделка объёма памяти в файле → «подпись не сходится», отказ
9.  неопознанная машина            → одна строка в очереди, счётчик отчётов
10. link -new                      → машина заведена, следующий отчёт опознан
```

Проверки кода: `gofmt`, `go vet`, `golangci-lint` — 0 issues; `go test -race` —
12 пакетов, 166 тестов. Кросс-сборка: `make agent` даёт `build/agent.exe`,
8,6 МБ, один файл.

### Прогон на настоящей Windows

Машина разработчика — Windows 10 Pro 19045, и собранный exe прогнали прямо на
ней. Это оказалось не формальностью: снимок пришёл заполненным, но с четырьмя
ошибками, которых не показал ни один тест.

**1. Коммутаторы Hyper-V считались настоящими сетевыми картами.**
`Win32_NetworkAdapter.PhysicalAdapter` отвечает «настоящая» для vEthernet
(WSL) и vEthernet (Default Switch) — они привязаны к физической карте. Хуже
того, настоящая карта в этом списке шла седьмой, и опознание взяло бы адрес
коммутатора WSL: тот меняется при переустановке WSL, то есть машина
превратилась бы в новую на ровном месте. Теперь виртуальным считается
интерфейс, на который указал ХОТЬ ОДИН признак, а не тот, на который указали
оба.

**2. Адаптер VirtualBox не выдавал себя ничем, кроме адреса.** Он называется
«Ethernet 2», и WMI считает его настоящим. Отличить можно только по началу
адреса — гипервизоры выдают себе адреса из известных диапазонов. Добавлена
проверка по ним: VMware, Hyper-V, VirtualBox, QEMU, Xen, Docker.

**3. Виртуальный диск Storage Spaces удваивал хранилище.** «Microsoft Storage
Space Device» на 930 ГБ собран из тех же дисков, что уже посчитаны, и в
карточку уходило 2085 ГБ вместо 1155. Теперь диск, которого нет среди
физических, в снимок не попадает — но только там, где список физических
вообще получен: на Windows 7 его нет, и правило отбросило бы все диски сразу.

**4. Мониторов собиралось ноль.** Признак «подключён сейчас» брался из
подраздела `Control` в реестре, а он под обычным пользователем не читается.
При этом реестр хранит ВСЕ мониторы, когда-либо подключавшиеся: на этой машине
их семь при двух подключённых — пять призраков, каждый из которых выглядел бы
в учёте как замена монитора. Теперь список подключённых спрашивается у WMI
(`WmiMonitorID`), а EDID по-прежнему читается из реестра: каждый источник
отвечает на тот вопрос, на который может ответить достоверно.

Плюс мелочь: `Win32_DiskDrive` называет диски SATA словом «IDE». Шина берётся
из `MSFT_PhysicalDisk`, где она названа правильно.

После правок снимок с этой машины: 1155 ГБ хранилища двумя дисками, одна
сетевая карта, два монитора, 71 программа, ни одной неудачи сбора. Файл
перенесён к службе и принят: машина опознана автоматически по SMBIOS UUID,
заведена, `host.first_seen` ушло в ленту, непубликованных сообщений в outbox
ноль.

### Чего проверить было нельзя

DoD этапа выполнен не полностью, и это надо назвать прямо.

| Из DoD | Состояние |
|---|---|
| Один exe | Проверено: 8,6 МБ, кросс-сборка из контейнера |
| Отдаёт заполненный снимок на Windows | Проверено на **одной** версии — Windows 10 Pro 19045. Остаются Windows 7 и 11 |
| Отчёт с машины без сети даёт тот же результат, что сетевой | Проверено, в том числе настоящим отчётом с этой машины |
| Ставится как служба | **Не проверено.** Код есть (`svc.Run`, `mgr.CreateService`, отложенный автозапуск, перезапуск при сбое), но ставить службу на машину разработчика без спроса нельзя |
| Переживает перезагрузку и сутки без сети | Буфер, повторы и растущая задержка проверены; перезагрузка — нет |

Сбор в контейнере через `/proc` и `/sys` написан не для парка, а ради того,
чтобы агента можно было прогнать целиком: расписание, буфер, повторы и задания
к платформе не привязаны, и без работающего сбора проверять их было бы не на
чем.

Остаток DoD закрывается на живых машинах: одна под установку службой и по
одной на Windows 7 и Windows 11. Опыт этого прогона говорит, что каждая
следующая версия системы найдёт своё: четыре ошибки на одной машине — это
ровно то, чего не видно из кода.

## 2026-09-04 · Комплект раскатки и правки после установки

Установка и удаление сведены к двойному щелчку: агента ставят на пятьсот
машин, и каждый шаг, который надо выполнить руками, — это машины, где шаг не
выполнили.

### Создано

| Файл | Что делает |
|---|---|
| `deploy/windows/установить.cmd` | Ставит или обновляет: сам поднимает права, сам решает, что делать |
| `deploy/windows/удалить.cmd` | Снимает службу и программу, каталог данных оставляет |
| `deploy/windows/удалить-полностью.cmd` | Снимает всё, включая отметку агента; спрашивает подтверждение |

`make agent` теперь собирает не файл, а папку `build/`: exe и три скрипта
рядом. Комплект раскатки — это папка целиком.

### Решения

**Токен раскатки — отдельным файлом `токен.txt`, а не строкой в скрипте.**
Скрипт ездит по сотням машин и попадает в системы контроля версий, а токен
даёт право зарегистрировать любую машину. Внутри скрипта он рано или поздно
окажется в репозитории.

**Установщик и обновление — один файл.** Если служба уже стоит, он
останавливает её, заменяет программу и запускает снова. Два похожих файла
рядом — это гарантия того, что однажды запустят не тот.

**Переустановка не требует токена.** Машина, где уже есть состояние агента,
пользуется прежним ключом. Требовать токен значило бы не дать переустановить
агента без похода к администратору за новым — а переустанавливают обычно
как раз тогда, когда что-то сломалось.

**Два варианта удаления, а не один.** Обычное оставляет каталог данных, и
машина после повторной установки остаётся той же карточкой в учёте. Полное
стирает отметку — после него машина попадёт в учёт как новая. Разница дорогая,
поэтому это разные файлы, а не флаг, и полное спрашивает подтверждение.

### Исправлено

**Русский текст в консоли превращался в кашу.** Go пишет в стандартный вывод
UTF-8, а консоль Windows разбирает байты в кодовой странице 866. Первое, что
видел администратор при установке, — нечитаемые строки. Агент теперь
переключает кодовую страницу на UTF-8 и **возвращает прежнюю при выходе**:
страница живёт не в процессе, а в самом окне, и оставить её изменённой значит
сломать вывод следующей команде, которую наберёт человек.

Возврат сделан явным вызовом, а не через `defer`: `defer` не срабатывает при
`os.Exit`, а выходов с кодом в этой команде несколько.

**Метки и имена переменных в скриптах — латиницей.** Кириллические зависят от
кодовой страницы окна, а скрипты поедут на машины с разными настройками.

**Сроки в журнале печатались наносекундами** — исправлено ранее в этот же
день, здесь проявилось на живой службе: после обновления в журнале стало
`"interval":"4h0m0s"` вместо `14400000000000`.

### Проверено

```
установить.cmd на машине со стоящей службой
  → служба остановлена, программа заменена, служба запущена
  → в журнале «агент остановлен» и «агент запущен» с читаемыми сроками

задание «собрать сейчас» службе
  → получено через опрос, выполнено, отчёт отправлен

программы пользователя под LocalSystem
  → 71 против 68 до правки: вернулись Chrome, VS Code, Postman, Python
  → ложного «программы удалены» больше нет

удалить.cmd и удалить-полностью.cmd
  → синтаксис и ход выполнения проверены на подменённых путях:
    обе ветви отрабатывают, сообщения выводятся, ничего лишнего не удаляется
```

Установка «с нуля» через `установить.cmd` и настоящее удаление на этой машине
не проверялись: запрос на повышение прав остался без ответа. Ветвь установки в
скрипте — то же самое, что уже отработало руками; ветвь удаления вызывает
`agent.exe uninstall`, проверенный кодом.

## 2026-09-04 · Диск, отданный в дисковое пространство, пропадал из отчёта

Найдено пользователем: в машине физически три диска — два по терабайту и SSD
на 240 ГБ, — а в учёт доехали два, на 1240 ГБ вместо 2240.

### Что происходило

Список дисков строился от `Win32_DiskDrive`, а `MSFT_PhysicalDisk` служил
дополнением: вид накопителя, шина, состояние. Связывались они номером диска.

На этой машине `Win32_DiskDrive` показывает не то, что есть:

```
1  WDC WD10EZEX-08WN4A1              931,5 GB
3  Microsoft Storage Space Device    930,0 GB
0  WDC WDS240G2G0A-00JH30            223,6 GB
```

Второго терабайтного диска в списке нет вовсе. Он отдан в дисковое
пространство, и система убирает такой диск из этого перечня, подставляя вместо
него виртуальный том. При этом `MSFT_PhysicalDisk` перечисляет все три
настоящих диска — с моделями, заводскими номерами, видом и состоянием.

Ирония в том, что вчерашняя правка «виртуальный диск Storage Spaces удваивал
хранилище» была верной по симптому и неверной по лечению: том действительно
считать нельзя, но выбрасывать его, оставаясь на `Win32_DiskDrive`, значит
терять диск, из которого он собран.

### Решение

Список строится от `MSFT_PhysicalDisk` — единственного источника, который
перечисляет именно физические диски и знает о них всё. `Win32_DiskDrive`
остаётся запасным путём для Windows 7, где этого класса ещё нет.

Побочно ушла и связка по номеру диска: `Index` в одном классе и `DeviceId` в
другом — разные пространства нумерации, совпадавшие здесь по случайности.

~ изменён `internal/collect/assemble.go` — `disks` разделена на
  `physicalDisks` и `legacyDisks`.
~ изменён `internal/collect/assemble_test.go` — тест переписан на настоящие
  данные с этой машины: три физических диска, один виртуальный том.

### Проверено

```
до:    WD10EZEX-08WN4A1 1000 ГБ · WDS240G2G0A 240 ГБ                → 1240 ГБ
после: WD10EZEX-08WN4A1 1000 ГБ · WD10EZEX-22MFCA0 1000 ГБ
       · WDS240G2G0A 240 ГБ                                          → 2240 ГБ
```

У всех трёх дисков заполнены заводские номера — раньше их не было ни у одного,
`Win32_DiskDrive` их на этой машине не отдавал.

Отчёт перенесён файлом в службу и доехал до карточки учёта: 2240 ГБ и три
накопителя в сводке. `gofmt`, `go vet`, `golangci-lint` — 0 issues, тесты
зелёные.

**Служба на машине разработчика по-прежнему на прежней сборке:** обновление
требует прав администратора. Обновить — двойной щелчок по
`build\установить.cmd`.

## 2026-09-04 · Административный вход: постановка заданий извне

Понадобился кнопке «Обновить сейчас» в учётной системе. Человек смотрит на
карточку компьютера, хочет свежие сведения сейчас, а не через четыре часа.

+ создан `internal/httpapi/admin.go` — `POST /v1/admin/hosts/{id}/collect`.
~ изменён `internal/config/config.go` — `ADMIN_TOKEN`.
~ изменён `internal/httpapi/health.go` — маршрут за ключом.
~ изменён `internal/commands/commands.go` — `AgentOfHost` в прикладном слое.
~ изменены `cmd/server/main.go`, `deploy/docker-compose.yml`, `.env.example`.
~ изменён `internal/httpapi/health_test.go` — 4 новых теста.

### Решения

**Нет ключа — нет маршрутов.** Не «маршрут есть, но всегда отвечает 401», а
`Router` их просто не регистрирует. Открытый вход, через который можно
поставить задание любой машине парка, не должен получаться случайно — из-за
незаданной переменной или опечатки в её имени. Тот же приём, что и с
маршрутами агента: нет проверяющего ключи — нет и приёма отчётов.

**Ключ сравнивается постоянным по времени сравнением.** Разница невелика, но
обычное сравнение строк завершается на первом несовпавшем байте, и по времени
ответа ключ подбирается посимвольно.

**Инвариант I1 цел.** Служба не знает, кто её просит: знает, что просящий
предъявил ключ. Ни слова про учётную систему в коде нет.

**Задание ставится машине, а не агенту.** Просящий знает идентификатор машины
из ленты и не знает ни про отметки агентов, ни про то, что их у машины за
жизнь было несколько. Агента находит служба.

### Проверено на живом стеке

```
без ключа                → 401
с ключом                 → 202, идентификатор задания
машина без агента        → 404 «у машины нет действующего агента»
агент на живой машине    → задание забрал и выполнил
```

`gofmt`, `go vet`, `golangci-lint` — 0 issues; тесты зелёные.

## 2026-09-07 · Этап 10 — эксплуатация · ВЫПОЛНЕН

Служба научилась рассказывать о себе, убирать за собой и держать утренний
всплеск.

### Создано

| Файл | Что в нём |
|---|---|
| `internal/metrics/` | Показатели и фоновый сборщик |
| `internal/storage/stats.go` | Показатели одним запросом |
| `internal/storage/retention.go` | Удаление устаревшего |
| `internal/retention/` | Чистка по расписанию |
| `internal/httpapi/admin.go` | (этап 9) административный вход |
| `deploy/prometheus.yml`, `deploy/alerts.yml` | Съём показателей и четыре тревоги |
| `deploy/grafana/` | Источник данных и панель из шести графиков |
| `scripts/backup-verify.sh` | Копия базы с проверкой восстановлением |
| Тесты | 1 новый, регрессия на раскатку |

### Что нашёл нагрузочный прогон

Ради этого этап и делается. Три захода, три находки — и все три сломали бы
раскатку на живом парке.

**1. Ограничитель частоты рассчитан на одиночку, а не на раскатку.** Первый
прогон: из тысячи машин зарегистрировались **десять**, остальные получили
«слишком много попыток». Групповая политика поднимает агента на сотнях машин
за минуты, и если служба стоит за обратным прокси, все они приходят с одного
адреса.

Разбор показал, что ограничитель защищал не то, что казалось. От подбора
токена он не защищает — токен это 192 случайных бита. От злоупотребления
утекшим токеном защищает не он, а счётчик использований: «токен на шестьсот
машин», и шестьсот первая не зарегистрируется с любой скоростью. Остаётся одно
— не дать одному источнику завалить службу запросами к маршруту без ключа.
Предел поднят до десяти в секунду и вынесен в настройку.

**2. Ограничитель восстанавливался в шестьдесят раз медленнее, чем читался.**
Второй заход дал 601 успешную регистрацию вместо тысячи. `newThrottle(600,
time.Minute)` читается как «шестьсот в минуту», а означало «шестьсот залпом и
одна в минуту»: второй аргумент был интервалом восстановления ОДНОЙ попытки.
Подпись переписана на «не больше N за окно», деление считается внутри.

**3. Симулятор не повторял попытку, а настоящий агент повторяет.** Он
существует ради того, чтобы вести себя как агент, — без повторов он проверял
не нагрузку на службу, а собственную нетерпеливость. Заодно выяснилось, что и
агент не повторял регистрацию: формально служба Windows перезапустилась бы по
действиям при сбое, но выглядело бы это как сломанная раскатка. Теперь
повторяет — четыре раза с растущими паузами и случайным разбросом.

### Definition of Done — проверено на живом стеке

```
тысяча машин, разброс старта минута
  отправлено 1000, не удалось 0
  снимков в базе: было 685, стало 1685 — ни одного потерянного
  очередь публикации: 0, лаг: 0
  служба: /ready 200
  среднее время приёма: 19,6 мс
```

Лаг потребителя виден на графике: панель «Лаг ленты» в Grafana
(`http://localhost:3001/d/inventory`), показатель `inventory_outbox_lag_seconds`.

### Решения этапа

**Показателей мало, и это осознанно.** Счётчик, который никто не смотрит,
стоит времени на каждом запросе и создаёт ощущение наблюдаемости там, где её
нет. Оставлены четыре вопроса, которые задают, когда что-то не так: доходят ли
отчёты, уходят ли они в ленту, кто молчит, где стало медленно.

**Главный показатель — не длина очереди, а её возраст.** Сто сообщений,
накопившихся за секунду, — норма; одно, лежащее час, — неполадка. Отсюда
`inventory_outbox_lag_seconds` рядом с `inventory_outbox_pending`.

**Время приёма — гистограммой, а не средним.** Утренний всплеск это хвост
распределения, а не сдвиг середины: среднее скрывает ровно то, ради чего его
смотрят.

**Молчащие берутся по отметке службы, а не пересчитываются.** Иначе два места
считали бы одно и то же по-разному, и однажды график разошёлся бы с событиями
в ленте.

**Тревог четыре.** Тревога, которая срабатывает раз в неделю без последствий,
через месяц перестаёт читаться — и вместе с ней перестают читаться настоящие.
Порог «часть парка замолчала» задан долей, а не штуками: пять молчащих из
пятисот это отпуска, пять из десяти — сломанная раскатка.

**Последний снимок каждой машины не удаляется никогда.** Иначе машина,
замолчавшая на два месяца, теряет в учёте всё, что о ней известно, и вместо
«сведения устарели» получается «сведений нет». История изменений не чистится
вовсе: она и есть ответ на вопрос «кто вынул диск и когда», а весит на три
порядка меньше снимков.

**Чистка внутри службы, а не заданием cron.** Cron живёт в чужой
ответственности, его забывают перенести при переезде, и обнаружить это можно
только по размеру базы через полгода. Служба, которая чистит за собой сама,
переезжает целиком.

**Копия проверяется восстановлением, а не фактом создания.** Копия, которую ни
разу не восстанавливали, — это файл, а не копия. Скрипт восстанавливает её в
отдельную базу и сверяет содержимое, включая читаемость JSON: повреждение
`jsonb` внутри дампа иначе обнаружится в день восстановления.

**Наблюдение за профилем compose.** Два контейнера едят память постоянно, а на
машине разработчика нужны не всегда: `make metrics` поднимает их явно.

### Новые команды

```
make metrics    поднять Prometheus и Grafana
make loadtest   утренний всплеск: make loadtest HOSTS=1000
make cleanup    разово удалить устаревшее
make backup     копия базы с проверкой восстановлением
```

### Зависимость

`prometheus/client_golang` — пятая. Своя реализация формата показателей
обошлась бы в сотню строк и разошлась бы с форматом при первом же изменении
стандарта; клиент делает ровно одну вещь и делает её правильно.

Проверки: `gofmt`, `go vet`, `golangci-lint` — 0 issues; тесты зелёные.

### Что осталось от этапа

Тревоги проверены только тем, что Prometheus их разобрал и посчитал:
`ПаркЗамолчал` перешла в pending на живых данных (двенадцать молчащих из
четырнадцати). Доставка тревог никуда не настроена — Alertmanager не поднят,
потому что адресат неизвестен: почта, Telegram или дежурный. Это решение
владельца, а не разработчика.

## 2026-09-07 · Разбор по живому вопросу: «нажимаю обновить, а сведения не обновляются»

Владелец нажал «Обновить сейчас» на карточке своего компьютера. Интерфейс
ответил «просьба принята». Дата сведений осталась прежней: 04.09, третьи
сутки.

Разбор занял двадцать минут и вскрыл четыре разных дефекта, из которых только
один был виден снаружи.

### Что оказалось на самом деле

Агент отработал безупречно — задание получено в 16:00:00, отчёт отправлен в
16:00:02. Служба его приняла, очередь публикации пуста, лаг ноль. Всё зелёное
с обеих сторон.

**Обмен с лентой стоял трое суток.** Контейнер потребителя живёт за профилем
compose, обычный `up -d` его не поднимает, и после перезапуска стека он не
вернулся. Служба копила, читать было некому.

Это и есть главный урок дня: две системы, каждая со своими показателями,
каждая зелёная, — и между ними трёхсуточная дыра, о которой ни одна из них не
подозревает. Показатели службы не могли этого увидеть в принципе: со своей
стороны она работала правильно.

### Четыре дефекта

**1. Обмен, остановившийся незаметно.** Исправлено отметкой «обмен жив»:
потребитель раз в пятнадцать секунд отмечается в кэше, страница
«Инвентаризация» показывает предупреждение, если отметки нет пять минут.
Отметка ставится и на пустом заходе — «сообщений нет» тоже работа, и именно
поэтому по ней можно отличить остановленный обмен от парка, в котором ничего
не менялось.

**2. Дата на карточке означала не то, что написано.** Подпись гласила
«сведениям 3 дн.», а считалась по `last_report_at` из ленты. Но состояние
машины уходит в уплотняемый топик только при расхождении — значит это поле
означает «когда последний раз что-то менялось». Машина, которая исправно
отчитывается каждые четыре часа и не меняется, выглядела брошенной.

Возраст сведений теперь считается по времени сбора снимка, а связь показана
отдельной строкой и берётся прямым запросом к службе — новый маршрут
`GET /v1/admin/hosts/{id}`.

Почему прямым запросом, а не через ленту: писать состояние на каждый отчёт —
это пятьсот одинаковых сообщений в час ради того, что не менялось. Публиковать
реже нельзя — человек стоит у экрана сейчас. Спрашивать по требованию
открытой карточки — один запрос там, где он действительно нужен.

Сообщение кнопки тоже стало честным: «дата сведений изменится, только если на
машине что-то поменялось». Без этой фразы кнопка на неизменившейся машине
выглядит сломанной всегда.

**3. Молчание считалось по тому же вранью.** Порог — неделя. Через неделю без
изменений — то есть в обычной жизни любой машины — учёт объявил бы молчащим
весь парк. Дефект ещё не проявился только потому, что обмену не исполнилось
недели.

Теперь молчание помечает служба и присылает в состоянии машины
(`silent_since`). Ради этого состояние публикуется ещё в двух случаях: при
уходе в молчание и при возвращении на связь. Второе не менее важно первого:
без него машина, которую увезли в отпуск на две недели, вернулась бы и
осталась помеченной молчащей до первой замены планки памяти.

**4. `first_seen_at` в учёте был «01.01.0001».** Поле объявлено контрактом,
показывается человеку — и никогда не заполнялось службой. Заполняется.

### Выбытие машины

Побочно вскрылось, что тысяча машин нагрузочного прогона, удалённая из базы
службы напрямую, при первом же чтении ленты приехала в очередь разбора учётной
системы. Уплотняемый топик хранит запись по ключу навсегда, и молча удалить из
него ничего нельзя — контракт это прямо описывает (§5), потребитель `retired`
ждал, а служба его никогда не публиковала.

Появился `agentctl retire`: помечает машину выбывшей и отправляет надгробие —
одной транзакцией, как всё остальное (I2). Работает и по идентификатору,
которого в базе уже нет: иначе машину, удалённую в обход службы, из топика не
достать ничем.

Надгробие несёт последний снимок. Пустое надгробие в уплотняемом топике
означало бы, что потребитель, поднятый через год, узнает о машине только факт
её списания и ничего больше.

### Пакет вместо набора файлов

`make package` собирает `build/пакет/` — папку, которую кладут в общую сетевую
папку целиком:

ЧИТАТЬ.txt     записка тому, кто откроет папку
```

**Адрес службы стал отдельным файлом.** Раньше он правился строкой внутри
скрипта, а скриптов теперь два. Два места для одного значения — это не
неудобство, а гарантия, что однажды будет поправлено одно из них и половина
парка раскатается на несуществующий адрес.

**Версия — файлом, а не запуском `agent.exe version` со share.** На машинах с
запретом запуска программ из сети скрипт иначе не смог бы сравнить версии и
обновлял бы всё подряд при каждой загрузке.

### Раскатка и обновление — один скрипт

`rollout.cmd` запускается сценарием запуска компьютера, то есть от имени
SYSTEM и без человека у экрана. Отсюда все отличия от ручного установщика:
ничего не спрашивает, ничего не ждёт, при нехватке данных пишет причину в
журнал и выходит с ненулевым кодом.

Он же обновляет — отдельного механизма нет намеренно. Машина, пропустившая
обновление, догонит его при следующей загрузке, и вести список отставших не
нужно.

**Молчаливый выход при совпадении версий.** Скрипт выполняется на каждой
машине при каждой загрузке. Строка «всё в порядке» в журнале превратила бы его
за месяц в бесполезную ленту, в которой настоящую ошибку уже не найти.
Проверено: код возврата 0, журнал не создан вовсе.

### Дефект: приём отчётов от существующих машин падал сутки

`can't scan into dest[0]: cannot scan NULL into *bool` — на каждом отчёте, с
21:13 предыдущего дня. Внесён накануне, вместе с признаком «машина вернулась
на связь».

Причина в SQL. Прежнее значение `silent_since` читалось общим выражением:

```sql
WITH было AS (SELECT silent_since FROM hosts WHERE id = $1 FOR UPDATE)
UPDATE hosts SET ... WHERE id = $1
RETURNING (SELECT silent_since IS NOT NULL FROM было), first_seen_at
```

Общее выражение блокирует ту же строку, которую меняет UPDATE, и скалярный
подзапрос в RETURNING получает пустой результат вместо значения. Запрос
синтаксически верен, компилируется и проходит все тесты. Правильная форма —
подзапрос в FROM:

```sql
UPDATE hosts h SET ...
  FROM (SELECT id, silent_since FROM hosts WHERE id = $1 FOR UPDATE) было
 WHERE h.id = было.id
RETURNING было.silent_since IS NOT NULL, h.first_seen_at
```

**Почему это не поймали.** Накануне сквозной путь проверялся новой машиной —
и она проходит другой веткой: `createHost`, а не `touchHost`. Проверка
успешно подтвердила, что работает ровно тот путь, который не ломался.

Исправлено в `make demo`: два отчёта с каждой машины вместо одного. Первый
идёт путём новой машины, второй — путём уже известной. На сломанном коде это
дало бы «отправлено 2, не удалось 2» вместо тишины.

**Что спасло данные.** Ни один отчёт не потерян: агент откладывал их в спул и
доставил все пять сразу после починки, вместе с тем, что накопилось за ночь.
Ровно ради этого спул и написан.

Заодно проверено, что того же приёма нет больше нигде в коде.

### Побочно: второй диск вернулся

Вместе с обновлением до 0.8.0 машина снова показала второй HDD:

```

disks               + HDD 931.5 ГБ WDC WD10EZEX-22MFCA0
```

В карточке учёта — 2240 ГБ и все три накопителя. Стоит последить: диск,
который то виден, то нет, — это либо разница версий агента, либо сама машина.

### Выбытие теперь отменяется отчётом

Проверка на живых данных вскрыла расхождение: машина, выведенная из учёта, но
продолжающая отчитываться, оживала у потребителей (состояние уходит без
признака `retired`), а в службе оставалась выбывшей. Две системы говорили
разное об одной машине.

Теперь отчёт снимает отметку выбытия так же, как снимает отметку молчания.
Значит вывели по ошибке либо не сняли агента; в обоих случаях отчёт — это
доказательство, и оно сильнее прежнего решения человека.

Проверено сквозь всю цепочку: выведенная вчера SIM-001 отчиталась снова — в
службе `retired_at` снят, в учётной системе `retired = false`.

### Третий ответ очереди разбора

В очереди накопилось одиннадцать записей — следы наладки: docker-контейнеры
без заводского признака, сценарии опознания, машины симулятора. Убрать их
штатно было нечем.

Оператор мог ответить очереди двумя способами: «это вот эта машина» и «это
новая машина». Обоих мало. Бывает третий случай — «это вообще не машина
парка»: чужой ноутбук в гостевой сети, тестовый контейнер, машина, списанная
полгода назад. Без такого ответа отчёт остаётся в очереди навсегда, а очередь,
в которой навсегда что-то лежит, перестают открывать.

`agentctl dismiss -report <id> -reason «…»` закрывает один отчёт,
`-all` — всю очередь разом (нужно ровно в одном случае: очередь наполнена
следами наладки). Отчёт не удаляется: остаётся отметка, кто и почему его
закрыл.

Очередь разбора службы очищена: закрыто 11, осталось 0.

## 2026-09-08 · Подпись кода, состояние службы словами, третий ответ очереди

### Решения владельца

Active Directory есть, но раскатка делается **без него** — «всё своё».
Подпись кода — **только бесплатный вариант**, но подпись желательна. Тревоги
— **никуда не слать**, показывать в интерфейсе.

### Подпись своим сертификатом

`deploy/windows/подпись/` — два скрипта: создание сертификата (один раз) и
подпись сборки (после каждой). Установщик и раскатка сами добавляют открытую
часть в доверенные корневые и доверенные издатели: без этого подписанный агент
ничем не лучше неподписанного — подпись есть, доверия к ней на машине нет.

Два хранилища, а не одно: `Root` — потому что сертификат самоподписанный и сам
себе корень, `TrustedPublisher` — потому что политики «только доверенные
издатели» смотрят именно туда.

**Проверка на живой машине нашла два дефекта в собственных скриптах.**

Первый: `Get-PfxCertificate -Password` появился только в PowerShell 6, а на
машинах администраторов стоит 5.1 — скрипт падал с «параметр не найден».
Заменено на `X509Certificate2`.

Второй тоньше и опаснее: успехом считался статус `Valid`. Сразу после подписи
статус на машине сборки — `UnknownError` «цепочка завершилась в недоверенном
корневом сертификате», и это **правильное** состояние: доверие к своему
сертификату появляется только там, где его установили. Скрипт объявлял бы
неудачей нормально подписанный файл. Теперь успех — это поставленная подпись с
меткой времени.

Метка времени обязательна и проверяется отдельно: без неё подпись перестанет
считаться действительной в день, когда истечёт сертификат, и агент, спокойно
работающий на пятистах машинах, вдруг станет неподписанным.

Закрытый ключ — право подписать любую программу так, что весь парк сочтёт её
доверенной. Каталог `ключи/` закрыт в `.gitignore` целиком.

### Состояние службы словами вместо Alertmanager

`internal/health` — те же четыре проверки, что и в правилах Prometheus, но
вычисленные самой службой и отданные по `GET /v1/admin/health` вместе с
показателями. Учётная система показывает их на экране инвентаризации.

Почему не Alertmanager: мониторинг разворачивают не везде и не сразу, а
человек, увидевший на экране устаревшие сведения, должен узнать причину там
же. У каждой неполадки есть ответ на вопрос «и что теперь» — тревога без него
через месяц перестаёт читаться вместе с полезными.

**Живая проверка сразу нашла ошибку в собственной проверке.** Служба
отрапортовала «ни одного отчёта уже 4 дн.» в момент, когда отчёты шли каждые
несколько минут: я взял `min(last_report_at)` — время самой давно
отчитывавшейся машины — вместо `max`. Пока отчитывается хоть кто-то, приём
работает, сколько бы ни молчали остальные; молчащих считает своя проверка.
Добавлено отдельное поле `LastReport`, и разница между «показатель парка» и
«показатель приёма» записана прямо в типе.

### Третий ответ очереди разбора

`agentctl dismiss` — «это вообще не машина парка». Подробности выше, в записи
за 7 сентября.

## 2026-09-15 · Наработка дисков: контракт обещал, агент не собирал

Поле `disks[].power_on_hours` было в контракте с первого этапа, описано как
«единственный признак, по которому видно, что диск отработал своё», — и агент
его никогда не заполнял. Теперь заполняет; агент — версия **0.9.0**.

### Путь к ответу и два неверных поворота

**Источник** — `MSFT_StorageReliabilityCounter`: доступен только администратору.
Служба агента работает от SYSTEM, так что в парке это не препятствие; разовый
запуск обычным пользователем честно пишет `disk_hours: Отказано в доступе` в
`failures`, а диски при этом остаются на месте — проверено.

**Первый поворот: перечисление класса.** Запуск с правами администратора прошёл
без единой ошибки — и без наработки у всех трёх дисков. Отличить «диски не
сообщают» от «счётчики не сопоставились с дисками» было нечем, а диагностика
в PowerShell с правами была отклонена.

Вместо того чтобы гадать, агент научился **сам называть причину** пустой
наработки в снимке: счётчиков нет вовсе; счётчики есть, но номера не совпали
(с обоими списками номеров); совпали, но часы нулевые. Если отказ в доступе
уже записан опросом, второй записи нет; на Windows 7 — ни слова. Это полезно и
в парке: причина видна на любой машине без отдельной диагностики.

**Второй поворот: причина оказалась не в дисках.** Снимок ответил «Windows не
вернула ни одного счётчика». Выглядело как «диски не сообщают» — но штатная
`Get-StorageReliabilityCounter` не перечисляет класс, а идёт от диска через
связь `MSFT_PhysicalDiskToStorageReliabilityCounter`. Агент переведён на тот же
путь: `ASSOCIATORS OF {MSFT_PhysicalDisk.ObjectId="…"}` для каждого диска.

```
WDC WD10EZEX-08WN4A1     6 049 ч
WDC WD10EZEX-22MFCA0    11 784 ч
WDC WDS240G2G0A-00JH30  20 512 ч      неудач нет
```

### Как устроено

По правилу `collect_windows.go` в нём только запросы. Всё, что можно проверить
на любой машине, вынесено и покрыто тестами:

* `reliability.go` — построение запроса. Идентификатор диска содержит кавычки
  и обратные косые черты; ошибка экранирования дала бы синтаксическую ошибку
  WQL, поэтому экранирование проверяется тестом;
* сопоставление счётчика с диском — сперва по диску, у которого спрашивали,
  потом по номеру устройства;
* объяснение причины — `наработкаНеСобрана`, и копия списка неудач, чтобы
  повторная сборка снимка из того же `Raw` не накапливала причины.

**В сравнение снимков наработка не входит** — это было заложено заранее
(`diskKeys`): иначе каждый диск «менялся» бы каждые четыре часа.

`gofmt`, `go vet` под Linux и под `GOOS=windows`, `golangci-lint` — 0 issues;
`go test -race` зелёные, +7 тестов в `internal/collect`. На живой машине:
обычный пользователь — диски на месте, причина «отказано в доступе»; с правами
администратора — наработка у всех трёх дисков.

**Не сделано:** установленная на машине разработчика служба агента по-прежнему

руками из контейнера и с этого ПК. Причина на стороне коммутаторов (строка
