# inventory_service

Служба сбора сведений о рабочих станциях корпоративной сети и агент, который
эти сведения отдаёт.

Служба самостоятельна: она знает только «компьютер», «диск», «сетевая карта» и
ничего не знает о своих потребителях. Учётная система — первый из них, но не
единственный. Всё, что уходит наружу, уходит в ленту событий, откуда любой
новый потребитель читает сам, не требуя правок здесь.

**Состояние:** выполнены этапы 0–6 из 12, этап 7 — частично. Серверная сторона
готова целиком: регистрация агента, приём под ключом, опознание машины,
сравнение с прошлым снимком, история изменений, события в ленту и очередь
заданий. Агент написан, проверен на живом стеке и поставлен службой на
настоящую Windows 10. Переживание перезагрузки и сбор на Windows 7 и 11 ждут
пилотных машин.

---

## Быстрый старт

Нужен Docker с compose v2. Локальная установка Go не требуется — всё, включая
тесты и линтер, запускается в контейнере.

```bash
cp .env.example .env
# задать POSTGRES_PASSWORD

make dev        # Linux, macOS, WSL
.\make.ps1 dev  # Windows: make не входит в поставку системы
```

| Что | Адрес |
|---|---|
| Служба | <http://localhost:8090> |
| Проверка живости | `/health` — жив ли процесс |
| Проверка готовности | `/ready` — доступны ли база и лента |
| Панель Redpanda | <http://localhost:9644/v1/status/ready> |

Порты смещены от стандартных намеренно: на той же машине работает учётная
система со своим Postgres на 5433.

На Windows — `.\make.ps1 <цель>` с теми же именами.

## Проверить, что путь отчёта работает

```bash
make migrate   # схема базы
make topics    # топики ленты
make demo      # регистрация -> отчёт -> база -> outbox -> релей -> лента
```

`make demo` заводит временный токен раскатки, регистрирует три вымышленные
машины, отправляет от них отчёты и печатает то, что дошло до ленты. Симулятор нужен не для красоты: агент появится только на
седьмом этапе, и без него всё до этого пришлось бы проверять на живых рабочих
станциях — то есть не проверять вовсе.

## Как машина получает право слать отчёты

Два разных секрета с разными правами:

| Секрет | Кто держит | Что даёт |
|---|---|---|
| Токен регистрации (`enr_…`) | Установщик, скрипт групповой политики | Только право обменяться на ключ. Ограничен сроком и числом машин |
| Ключ агента (`inv_…`) | Одна машина | Право слать её отчёты. Отзывается по одной машине |

```bash
make token LABEL="раскатка сентябрь" DAYS=14 USES=600   # печатается один раз
make agents                                              # кто на связи, кто отозван
make revoke AGENT=<отметка> REASON="машина списана"
```

Токен показывается один раз — в базе лежит только его хеш. Ключ агента тоже:
служба хранит хеш и первые символы, чтобы человек мог узнать ключ в списке.

Отметка агента берётся **из ключа**, а не из тела отчёта. Иначе машина с
действующим ключом присылала бы отчёты от имени соседа и переписывала его
карточку.

## «Обновить сейчас»

Сервер сам к машине не стучится: она может быть дома, в командировке или
просто выключена. Но причина важнее технической — если бы сервер умел отдавать
команды пятистам компьютерам, то тот, кто однажды получит доступ к серверу,
получил бы и всю сеть.

Поэтому задание кладётся в очередь, а агент забирает его при ближайшем опросе:

```bash
make collect HOST=PC-214-01   # поставить задание
make tasks                     # что в очереди и что с ним стало
```

Видов заданий ровно два, и список закрыт **в контракте**, а не в службе:
`collect_now` и `set_interval`. Агент сверяет полученное с этим списком и
отказывается от всего остального — не «сервер прислал строку, выполним», а
«сервер может попросить одно из двух».

Выдача не окончательна: у задания есть аренда в пять минут. Агент упал сразу
после получения — задание вернётся в очередь, а не пропадёт навсегда.

## Когда служба считает, что что-то изменилось

Сравнивается не весь снимок, а перечисленный в коде список полей. В снимке
полно того, что меняется само по себе: время последней загрузки, наработка
диска в часах, адрес VPN-адаптера, забытая в машине флешка. Сравнивай снимки
целиком — и девятнадцать отчётов из двадцати давали бы «изменилось», а
настоящая замена диска утонула бы в этом потоке.

Быстрый путь — отпечаток по тем же полям: сравнить два хеша дешевле, чем
разобрать и сличить два снимка.

| Событие | Когда |
|---|---|
| `host.first_seen` | Машина заведена в реестре службы |
| `host.changed` | Есть фактическое расхождение с прошлым снимком |
| `host.silent` | Машина молчит дольше порога. Уходит один раз, а не на каждом проходе |
| `host.unresolved` | Отчёт не удалось отнести к машине |

История изменений живёт дольше снимков: снимки чистятся по сроку, а история —
это и есть ответ на вопрос «кто вынул диск и когда».

## Агент на рабочей станции

Один exe на все случаи. Собирается кросс-сборкой из контейнера: `make agent`
кладёт `build/agent.exe`.

```
agent install -server http://inventory:8080 -token enr_…   поставить службой
agent once                     снять и отправить один раз
agent once   -out X:\отчёты    снять в подписанный файл: машина без сети
agent status                   что агент знает о себе
agent uninstall                снять службу
```

Установка одной командой — потому что раскатка идёт скриптом групповой
политики, и каждый лишний шаг в нём означает машины, на которых шаг не
выполнился.

Что агент делает сам, без сервера:

| | |
|---|---|
| Сбор по расписанию | Раз в четыре часа, со случайным сдвигом. Иначе пятьсот машин ходят в службу строем |
| Первый сбор не сразу | Пятьсот машин включаются утром в одни и те же десять минут |
| Буфер на диске | Нет сети — отчёт ложится в очередь, до двухсот штук, старые вытесняются |
| Растущая пауза при неудаче | Служба, лежащая под нагрузкой, не должна получать по попытке в минуту от каждой машины |
| Свой журнал | `agent.log` рядом с данными, сменяется по размеру |

### Комплект раскатки

`make package` собирает папку `build/пакет/` — это и есть то, что кладётся в
общую сетевую папку или переносится на машину:

```
agent.exe                программа
version.txt              версия в пакете (по ней раскатка решает, обновлять ли)
server.txt               адрес службы, один на весь пакет
token.txt                токен раскатки (кладёт администратор)
установить.cmd           поставить или обновить, два щелчка
удалить.cmd              снять службу, данные оставить
удалить-полностью.cmd    снять всё, включая отметку агента
rollout.cmd              то же самое для групповой политики, без человека
ЧИТАТЬ.txt               записка тому, кто откроет папку
```

Раскатка по парку — [docs/РАЗВЁРТЫВАНИЕ.md](docs/РАЗВЁРТЫВАНИЕ.md).

Установка — двойной щелчок по `установить.cmd` и подтверждение запроса
Windows. Права скрипт поднимает сам; адрес службы берётся из `server.txt`,
токен — из `token.txt` рядом.

Токен намеренно лежит отдельным файлом, а не внутри скрипта: скрипт ездит по
сотням машин и попадает в системы контроля версий, а токен даёт право
зарегистрировать любую машину.

Тот же `установить.cmd` служит и обновлением: если служба уже стоит, он
останавливает её, заменяет программу и запускает снова — токен при этом не
нужен.

Два варианта удаления не для удобства. `удалить.cmd` оставляет каталог данных,
и машина, на которую агента поставят снова, останется той же карточкой в
учёте. `удалить-полностью.cmd` стирает и отметку — после него машина попадёт в
учёт как новая, и старую карточку придётся объединять руками. Он спрашивает
подтверждение и нужен только при выводе машины из эксплуатации.

### Что появляется на машине

| Где | Что |
|---|---|
| `C:\Program Files\inventory-agent\` | `agent.exe` |
| `C:\ProgramData\inventory-agent\` | `config.json`, `state.json`, `agent.log`, `spool\` |
| Служба `InventoryAgent` | LocalSystem, автозапуск отложенный, перезапуск при сбое |
| `HKLM\SYSTEM\CurrentControlSet\Services\InventoryAgent` | Единственная ветка реестра |

Ни автозапуска в `Run`, ни заданий планировщика, ни правил брандмауэра:
соединения только исходящие. `agent uninstall` снимает службу, но **не трогает
каталог данных** — в нём отметка агента, и удалить её значит завести машине
вторую карточку в учёте.

Журнал — UTF-8, а PowerShell 5.1 по умолчанию читает файлы как ANSI:

```powershell
Get-Content 'C:\ProgramData\inventory-agent\agent.log' -Tail 20 -Encoding UTF8
```

Сервер к машине не стучится никогда: она может быть выключена, дома или за
NAT. Всё, что он может, — положить задание в очередь и ждать, пока агент за
ним придёт.

## Машина без сети

Такие машины в парке есть, и для них весь обмен разворачивается в одну
сторону: агент кладёт файлы на флешку, человек несёт флешку к службе.

```bash
# на машине без сети
agent enroll -out X:\отчёты -token enr_…    заявка на регистрацию
agent once   -out X:\отчёты                 подписанный отчёт

# у службы
make import DIR=X:\отчёты
```

Отчёт подписан ключом машины. Без подписи файл, принесённый на флешке, — это
способ записать в учёт что угодно от имени любой машины: достаточно поправить
в нём имя и объём диска.

Подпись проверяется **открытым** ключом, который машина отдала при
регистрации. Общий секрет тут не годится: служба и по сети хранит только хеш
ключа машины, и чтобы проверять им подпись, пришлось бы держать ключи всего
парка в открытом виде.

Дальше файл идёт тем же путём, что сетевой отчёт: те же проверки, то же
опознание, та же лента. Повторный приём тех же файлов безвреден — снимок с тем
же временем сбора служба уже видела.

## Как система узнаёт, что это та же самая машина

Опознание идёт по цепочке признаков, от надёжного к слабому: отметка агента →
заводской номер → SMBIOS UUID → адрес сетевой карты. Один признак принадлежит
не более чем одной машине — это ограничение базы, а не соглашение.

По слабому признаку машину можно **найти**, но нельзя **завести**: сетевую
карту переставляют, и запись, созданная по одному лишь адресу, завтра окажется
чужой.

Три случая уходят человеку в очередь разбора, потому что автоматика ошиблась
бы молча:

| Случай | Как выглядит |
|---|---|
| Признаки указывают на разные машины | Сетевую карту переставили из одной машины в другую |
| Под известной отметкой другой заводской номер | Клон виртуальной машины или замена материнской платы |
| Нет ни одного надёжного признака | Сборная машина без заводского номера |

```bash
make pending                       # что ждёт разбора и почему
make link REPORT=<id> HOST=<id>    # это уже известная машина
make link-new REPORT=<id>          # это новая машина: завести
```

Две команды, а не одна, потому что случаи разные. Сборный компьютер без
заводского номера попадает в разбор при первом же появлении, и связывать его
не с чем — машины в базе ещё нет; там человек говорит «да, это новая машина».
Переставленная сетевая карта — наоборот: машина есть, и вопрос лишь в том,
какая именно.

После разбора признаки закрепляются за машиной, и следующий её отчёт
опознаётся сам. Сам отложенный снимок при этом не применяется: он уже устарел,
а свежий придёт через несколько часов.

Неопознанная машина занимает в очереди одну строку, а не по строке на отчёт:
она продолжает отчитываться каждые четыре часа, и без этого очередь за неделю
перестала бы быть списком дел. Счётчик рядом показывает, сколько раз она
приходила.

## Разделение живости и готовности

`/health` отвечает, пока процесс жив, и **не проверяет зависимостей**.
`/ready` проверяет базу и ленту.

Разница не косметическая: если подмешать зависимости в проверку живости, то
перезапуск базы начнёт убивать саму службу — оркестратор сочтёт её мёртвой и
перезапустит, хотя чинить надо не её. Готовность при этом честно скажет «не
готова», и трафик на неё не пойдёт.
